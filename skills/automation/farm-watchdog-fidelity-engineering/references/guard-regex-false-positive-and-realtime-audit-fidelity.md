# Rolling-Window Audit vs Historical Fixes & Guard Regex False-Positive Traps

## 1. Context & Problem Statement
During 6-hour farm compliance audits (`gate_compliance_watchdog.py`), operators frequently observe reports remaining in `FAIL` status with high violation counts (e.g., 34 `GUARD_DANGEROUS_ROOT`, 23 `subagent_edit_blocked`) despite numerous previous sessions declaring those issues "fixed" or "auto-rewired".

This discrepancy stems from two distinct mechanisms:
1. **Conflating Historical Script Fixes with Real-Time Session Telemetry**:
   - A 6-hour watchdog audits events generated by live agents and workers in the preceding 6 hours.
   - Fixing a rule (e.g. auto-rewiring `GUARD_SEARCH_FILES_ROOT` or adding test mock filters) eliminates *that specific defect* (which indeed dropped from 40+ to 0).
   - However, if concurrent foreground sessions continue issuing unparameterized commands (e.g., raw `delegate_task` to edit code instead of `dispatch_worker.py`, unparameterized `adb` without `-s`, or unbudgeted timeouts), the watchdog accurately logs and reports those live violations.
2. **Guard Regex False-Positive Traps (The `FIND_SCAN` & `//` Integer Division Trap)**:
   - Overly broad guard regex patterns intended to catch malicious shell commands (e.g. Linux `find` or root scans on `/`) mistakenly match benign inline Python code.
   - Example incident: A harmless PIL image-processing snippet:
     ```python
     python -c "
     from PIL import Image
     im = Image.open('D:/Taadaa/orders/images/order_20261029_004_raw.jpg')
     # Find center phone bounds: phone screen has white background
     mid_x = (min(white_xs) + max(white_xs)) // 2
     "
     ```
     was repeatedly intercepted and blocked as `GUARD_DANGEROUS_ROOT`:
     - `FIND_SCAN = re.compile(r'(?<![\w.-])find(?:\.exe)?\s+[^\n]*', re.I)` matched `# Find center...` inside the Python comment.
     - `contains_dangerous_root` matched `//` in Python integer division `// 2` as a standalone Unix root `/` or `//`.
     - Coupled with `D:/Taadaa` in the path string, this generated 34 false-positive blocks, falsely skewing the watchdog report.

---

## 2. Invariant Contracts

### Contract 1: Command-Boundary & Syntax Discrimination for Shell Guards
- Guard regexes matching Unix/DOS utilities (`find`, `ls`, `grep`, `dir`) MUST NOT match inline comments, docstrings, or language-specific constructs inside `python -c` or script heredocs.
- Utilities MUST be anchored to command boundaries: start of string, after pipes `|`, or after command separators (`;`, `&&`, `||`).
- Root path matching MUST NOT treat Python integer division `//` as a filesystem root.

### Contract 2: Diagnostic Protocol for "Why is the 6H Report Still Failing?"
When diagnosing an unexpected `FAIL` in rolling compliance reports:
1. **Deconstruct by Timestamp and Source**: Parse raw entries from `guard_scan_audit.jsonl` and `dispatch_audit.jsonl` in the exact window (`start` to `end`).
2. **Distinguish Real Live Violations from Guard Bugs**:
   - Inspect the actual `target` command that triggered the block.
   - If the command is benign (e.g. image processing, arithmetic, single-file reading), classify as **Guard Regex False Positive** and patch the guard hook's boundary matcher.
   - If the command actively violated protocol (e.g. subagent prompt attempting to rewrite protected code), classify as **Live Operational Violation** and enforce coordinator/worker discipline.
3. **Acknowledge Fixed Invariants**: Validate that previously fixed rules (e.g. `GUARD_SEARCH_FILES_ROOT`, `CONSOLE_WINDOW`) remain absent from the top violations list to prevent demoralizing operators into believing "fixes don't work".
