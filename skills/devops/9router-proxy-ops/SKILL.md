## DeepSeek reasoning mode — THE pitfall
- **Never put `(max)`/`(high)` in the model name** for commandcode connections. 9router passes the raw model string upstream → commandcode replies **403**: `Model/provider not recognized: anthropic:deepseek/deepseek-v4-flash(high)`.
- **Never prefix OpenAI-registry ids with `codex/`** (Codex adds it for built-in models when routed via a custom provider): 9router returns misleading `401 Your authentication token has been invalidated` — the id is just unknown upstream (not an auth problem). `codex/gpt-5.6-luna` fails; `deepseek-v4-flash`/`cmc/*`/`oc/*` (no prefix) work. Full recipe + evidence: `references/codex-profile-fallback-9router.md`.
- Reasoning must travel as a **body param**. Hermes sends `extra_body.reasoning = {"enabled": true, "effort": "max"}` (OpenAI SDK merges `extra_body` into the JSON body).
- DeepSeek V4 accepts only `low` | `high` | `max` (Hermes `DEEPSEEK_V4_REASONING_EFFORTS`). Anything else (medium/auto) → provider default.
- 9router console-log prints `THINK:<mode>` from the *translated* body: `output_config.effort` → `thinking` → `reasoning_effort`/`reasoning.effort` → `thinkingConfig`. **`THINK:auto` is a DISPLAY LABEL, NOT a reliable indicator of whether reasoning runs** (verified 2026-08-06): a stream request carrying `reasoning:{enabled:true,effort:"high"}` still logs `THINK:auto` while the model returns `reasoning_content` chunks. Root causes: the label reads effort from the translated body where it may sit in `reasoning.effort` (object) instead of top-level `reasoning_effort`, and `providerThinking.commandcode.mode` was set to invalid `"thinking"` (falls through → auto). User's ruling: the label doesn't matter — only actual reasoning behavior does. Never conclude "not reasoning" from `THINK:auto`; use the stream probe below.
- Hermes resolves reasoning at **session init** (`resolve_reasoning_config`); config edits need a **new session** (`/new`) to take effect. `agent_runtime_helpers.py` also re-resolves on `/model` switch — so `/new` **or** `/model` switch applies a changed `reasoning_effort` without full restart. agent.log does NOT print the resolved effort per call; to know what a live session is sending, check when the session started vs when config was last changed (config mtime via `stat -c %y`) — a session started before the config edit still holds the old effort until `/new` or a model switch.
- Change effort: `hermes config set agent.reasoning_effort max` (or per-model `agent.reasoning_overrides.<model>: high`), then new session.
- **9router translate layer FORCES the effort (verified 2026-08-06).** chunk `8499.js` deepseek case:
  ```js
  case"deepseek":{b.thinking={type:"enabled"};let a=n(j); // j = providerThinking.commandcode
    b.reasoning_effort = "xhigh"===a||"max"===a ? "max" : "high"; break}
  ```
  With `providerThinking.commandcode.mode="high"` → `a="high"` → **every deepseek request gets `reasoning_effort="high"` regardless of what the client sent** (max included). To get real max you must set `providerThinking.commandcode.mode="max"` — client-side `reasoning:{effort:"max"}` does NOT survive translate. Earlier conclusion "client effort is respected" was based on ONE noisy run (9943 vs 7104 reasoning chars) — repeated A/B (4 runs, hard TSP question, same max_tokens cap) showed high and max produce IDENTICAL reasoning output. **Lesson: never trust a single probe run for reasoning-effort A/B; repeat 3+ times.** This also means the bulk `flash/max → flash/high` edit + `agent.reasoning_effort: high` are both correct AND redundant — the proxy forces high anyway. `/new` not needed to change reasoning (old sessions sending max are still forced to high at translate).
- **`low`/`medium` do NOT exist for `cmc/deepseek/*` — everything collapses to high (verified by live probes 2026-08-06).** Sending `effort:"low"` (top-level or `reasoning.effort`) produced the SAME reasoning volume as `high` (~1300-1900 chars on a hard partition problem, overlapping). The translate ternary `"xhigh"===a||"max"===a?"max":"high"` has exactly two outputs: max or high. User asked "set low cũng k được à?" — correct: only `providerThinking.commandcode.mode="max"`/`"xhigh"` yields max; low/medium/auto/thinking/invalid all → high. If real low effort is needed, use `oc/*` models (effort respected) or a non-9router route.\n- **User ruling 2026-08-06: deepseek-v4-flash runs `high` everywhere** (Hermes `agent.reasoning_effort: high`, 9router `providerThinking.commandcode.mode: "high"`, orchestration AGENTS.md pins bulk-edited `flash/max` → `flash/high`). `max` reserved for deep-reasoning cases. high vs max: ~same quality on routine tasks; max burns 1.5–3× reasoning tokens + latency on hard problems. Do not silently bump back to max.
- Bulk-edit orchestration pins across repos (D:\Taadaa AGENTS.md + HERMES_SUBAGENT_RULES.md + consumer AGENTS.md): replace `deepseek-v4-flash/max`→`deepseek-v4-flash/high`, `flash/max`→`flash/high`, `reasoning_effort=max`→`reasoning_effort=high`, and backtick form `` `deepseek-v4-flash`/`max` ``→`` `deepseek-v4-flash`/`high` ``. **Only the flash/deepseek side — leave `gpt-5.6-luna/max`, `Sol/max`, `Terra/high` untouched.** Backup each file (`cp f f.flash-high-<ts>.bak`) first. Windows quirk: Python `open(f,'w')` raised PermissionError on 7 files while **bash `sed -i` wrote them fine** (MSYS path/encoding) — if python write fails, use bash sed instead of declaring the file locked. Also grep for `deepseek-v4-flash.*max` after sed — the backtick-slash form on AGENTS.md:1416 didn't match the plain patterns.

## Gemini/Antigravity runtime fallback verification
- Do not infer a live three-layer chain from `.env`, screenshots, source code, unit tests, or the presence of proxy rows. Verify the running process, its actual DB, scope precedence, and a fresh canary.
- OmniRoute may use `C:\\Users\\<user>\\.omniroute\\storage.sqlite`, separate from 9Router's `AppData\\Roaming\\9router\\db\\data.sqlite`.
- Account-scope proxy resolution returns before provider scope; an account pinned to `test.taadaa.click:<port>` does not automatically fail over to `mirotik1.taadaa.click` unless routing code explicitly implements cross-scope fallback.
- `PROXY_FAIL_OPEN=true` in `runWithProxyContext` can call `runDirect()` after that helper sees an unreachable proxy. It does not make account resolution walk into the provider pool and cannot rescue a pre-dispatch `ALL_TARGETS_SKIPPED` combo failure.

## Hermes session-reset and provider-failure triage (verified 2026-08-13)

- `Invalidated run generation ... (session_reset)` is a **Hermes Gateway internal event**, not a 9Router reset. It can come from automatic expiry, `/new`, `/reset`, or stale-session recovery. The reliable proof is the session routing key in `gateway.log`: `agent:main:telegram:<scope>:<chat-or-group>:<thread>`. A `/new` response sent to a different chat/thread proves only that other session was reset.
- For Telegram, correlate both sides before claiming a command affected a session: (1) `inbound message ... msg='/new'` or `msg='/restart'` with the exact chat/thread, and (2) `Sending command '/new' response` / command handling for the same routing key. `/restart` may be a user message or an operational gateway restart request; do not infer it changed every Telegram session.
- If the screenshot says `Session automatically reset (inactive for 24h)` but current YAML says `session_reset.mode: none`, distinguish **old reset history** from a live reset: check the reset timestamp, the gateway process start/effective config, and the exact routing key. Do not blame 9Router or assert that `mode: none` protected a session that was already reset before the config was loaded.
- `The model provider failed after retries` is a separate provider event. In this incident the evidence was `opencode-audit` → `Streaming response failed: [504] Upstream idle timeout exceeded`, followed by Hermes retries/fallback. A separate `provider=cockpit ... model=gpt-5.6-luna ... cannot convert float infinity to integer` is a Cockpit metadata/usage-path error, not proof that the 9Router `cx/gpt-5.6-luna` combo failed.
- **User-facing workflow:** report the exact chat/thread and log evidence first; do not say “Hermes reset everything” from a banner alone. Do not restart a live gateway merely to apply a config change while farm jobs or Telegram sessions are active; warn about disruption and prefer a new session where the setting is session-scoped.
