## All API products means every connected supplier

When the user asks for “link lọc all sản phẩm qua API”, “all API hiện tại”, or corrects a narrow supplier-only link:

1. Treat the scope as `products.supplier_id > 0`, not `supplier_id = <named supplier>`. Query live `suppliers` and product counts first; never infer the total from `clonefbig`/`fbclone` alone.
2. Separate API products from manual uploads explicitly: `supplier_id > 0` + non-empty `api_id` is API-linked; `supplier_id = 0` is manually uploaded. Report total and per-supplier counts.
3. Inspect the admin filter implementation. If it only supports exact numeric IDs and `none`, add a minimal `api` branch (`AND supplier_id > 0`) plus a dropdown option, with no DB mutation. Preserve exact supplier and manual filters. Deploy theo playbook "deploy một admin view file lên live" (backup+MANIFEST, lint, atomic mv).
4. Verify the deployed filter with the live DB count and an unauthenticated HTTP probe (redirect to login is acceptable; HTTP 500 is not). Then send the single authenticated admin URL:
   `https://doravo.net/?module=admin&action=products&supplier_id=api&limit=100`
   State clearly that login is required. Do not send the old supplier-specific `supplier_id=1` link as the answer to an all-API request.
5. Do not equate labels such as `fbclone`, `fbclonefb`, and `clonefbig` without a live `suppliers.id + type + domain + status` match. Any Telegram price watcher must state its exact supplier scope; a watcher for `clonefbig` is not proof of coverage for another supplier.

## Phân biệt hàng API vs hàng up tay (manual) + đối chiếu giá với bảng giá ngoài

Trigger: user hỏi "sp này API hay up tay?", "giá này set lâu chưa / giá gốc là bao nhiêu", hoặc mang bảng giá bên ngoài (Telegram/người bán) hỏi "giá web tao có khớp không".

- API: `products.supplier_id > 0` + `api_id` có giá trị, `cost` = giá nguồn. Up tay: `supplier_id = 0` + `api_id IS NULL`, `cost` thường = 0 → "giá gốc" KHÔNG nằm trong DB, phải tra từ nguồn nhập; đừng hứa trả cost từ DB.
- Khi user nhờ "sửa/check giá sp đang để X": LUÔN đọc DB trước — user nhớ sai hoặc sp đã bị đụng tay cùng lúc (2026-08-16: user tin sp 57 up tay đang 0.14, thực tế 2.915đ = $0.11). Sp up tay song song cùng category + tên gần giống sp API (cat 6: 57 up tay vs 56 API, tên chỉ khác "Clone") dễ nhầm — xác định row qua `supplier_id`/`api_id` trước khi UPDATE. Giá USD hiển thị = price VND ÷ 26.500 (bảng `currencies`): $0.14 = 3.710đ, $0.12 = 3.240đ. Sp 56 tên nguồn có hậu tố "2FA On" LẶP 2 lần (lỗi tên nguồn, không phải lỗi nhập).
- Hỏi "giá set lâu chưa?": so `update_gettime` vs `create_gettime` — bằng nhau = giá chưa từng sửa từ lúc tạo (vd TikTok 0.17$ id 38/40 tạo 07-07/09-07-2026, update == create → giá cũ, không phải vừa set). Supplier cron chỉ đụng `update_gettime` của row API, row manual không bao giờ bị cron ghi đè.
- Tỷ giá hiển thị shop: bảng `currencies` (VND rate=1 default, USD rate=26500) — KHÔNG dùng `settings` gateway rates (crypto_rate/paypal_rate/perfectmoney_rate...) để quy đổi giá sp; đó là rate cổng thanh toán.
- Đối chiếu giá với bảng giá ngoài: dump toàn catalog 1 query, map theo CLASS sản phẩm không theo chuỗi tên ("FB real no 2FA 2$" ≠ "FB Clone No 2FA 2400đ" — khác chủng loại, báo class mismatch thay vì coi là lỗi giá; "Twitter 2025 search top" khớp cả 2 SKU X search top). Chi tiết + SQL: `references/manual-products-and-price-cross-check.md`.

## Hotmail Checklive Admin Tool (`ajaxs/admin/hotmail-checklive.php` & `api/checklive_hotmail.php`)

- **Format bắt buộc:** `email|password|refresh_token|client_id` (hoặc định dạng Full info có thêm recovery mail ở đuôi). `client_id` phải chuẩn UUID regex (`^[0-9a-fA-F]{8}-...`).
- **Cơ chế:** Gọi trực tiếp Microsoft OAuth2 token endpoint (`https://login.microsoftonline.com/consumers/oauth2/v2.0/token`) bằng curl multi song song:
  - `HTTP 200` + có `access_token` $\rightarrow$ **LIVE**.
  - `HTTP 400` + `invalid_grant` $\rightarrow$ **DIE** (token bị huỷ, đổi pass, hoặc acc bị khoá).
  - Lỗi curl / HTTP khác $\rightarrow$ **UNKNOWN** (không đánh DIE để tránh xoá nhầm khi mạng chập chờn).
- **Pitfall:** Nếu ném `email|password` thuần (Hotmail loại 1) vào tool này, tool sẽ báo lỗi ngay *"Không có dòng nào đúng định dạng email|password|refresh_token|client_id"* vì Microsoft đã tắt hoàn toàn Basic Auth trên web/IMAP từ 09/2022; tool check web bắt buộc phải có OAuth2 token (Hotmail loại 2). Hotmail loại 1 phải check/login qua Outlook App trên farm Android.

## Playbook: hide non-target API products while preserving manual inventory

Trigger: user asks to hide all API products except a named supplier (for example, “chỉ chừa CloneFBIG”), while manual products must remain visible.

2. Define scope explicitly before writing: preserve manual `supplier_id=0`; preserve target supplier `supplier_id=1`; hide only other API rows: `supplier_id>0 AND supplier_id<>1` (use `supplier_id>1` only after confirming this site's IDs are positive and suitable). Safe mutation: `UPDATE products SET status=0 WHERE supplier_id>0 AND supplier_id<>1 AND status=1;` — status only, no deletion, price, stock, category, or API-field changes.
3. Read-only preflight must report counts by scope/status and target visible count. This catches the common mistake `supplier_id<>1`, which would also hide manual rows. If the user corrects the scope, re-probe before writing and do not rely on a queued worker plan.
4. Backup affected rows server-side before mutation under `/var/www/shopclone7/backups/pre-hide-other-api/<UTC timestamp>/`; dump at least `id,supplier_id,status,name,price,cost,category_id,api_id`, write a manifest with condition and row count, verify non-empty, and never print credentials/API keys.
5. Execute one scoped UPDATE, then independently verify: target supplier remains visible, manual visible count is unchanged, non-target API visible count is zero, and non-target API hidden count equals the before count. Verify no products were deleted and no unrelated columns were written.
6. Report exact before/after counts and absolute backup path. If the first proposed scope was too broad, explicitly state whether it was not executed or was corrected before mutation; never claim success from a worker report without parent-side verification.

## SSH access — pitfalls (state 2026-08-13: ĐÃ HOẠT ĐỘNG)

- **SSH hiện HOẠT ĐỘNG**: `ssh -i ~/.ssh/doravo_deploy root@152.42.187.200` OK (key ed25519, KHÔNG passphrase, đã authorized). Hostname VPS = `test`. Kiểm nhanh: `ssh -i ~/.ssh/doravo_deploy -o BatchMode=yes root@152.42.187.200 'echo OK'`.
- `45.76.187.121` = **IP CŨ** (host key changed — server cũ đã cài lại/bỏ). KHÔNG dùng; gặp HOST_KEY_CHANGED khi SSH IP này là chuyện bình thường.
- Lịch sử 2026-08-11: HANDOFF ghi `~/.ssh/do_web01_vps` đã bị xoá; `~/.ssh/doravo_deploy` lúc đó CHƯA authorized → Permission denied. User đã tự add pubkey sau đó. Nếu SSH fail nữa, diagnostic theo thứ tự dưới đây.
- Diagnostic khi SSH fail (đúng thứ tự):
  1. `ls -la ~/.ssh/` — key nào tồn tại thật so với docs.
  2. `ssh -o BatchMode=yes -i <key> root@<ip> "echo OK"` — BatchMode loại passphrase khỏi phương trình.
  3. Key encrypted? `grep -c bcrypt <keyfile>` — 0 = không mã hoá → fail là *authorization*, không phải passphrase.
  4. Thử nhiều user (root/ubuntu/deploy); ping host + `curl -L https://doravo.net/` xác nhận site sống.
  5. Host key trong known_hosts khớp (không HOST_KEY_CHANGED) = VPS còn nguyên vẹn, chỉ thiếu authorized key.
- Kiểm site sống: `curl -sS -o /dev/null -w "%{http_code}" -L https://doravo.net/` → 200.
- **Path repo ≠ path live**: repo có prefix `SHOPCLONE7/` (vd `SHOPCLONE7/libs/stock_alert.php`) nhưng live là `/var/www/shopclone7/current/libs/stock_alert.php` — KHÔNG có `SHOPCLONE7/`. Diff/scp nhầm path cho file rỗng âm thầm; luôn map đúng.
- **MSYS `~` vs `$HOME` trong chuỗi lệnh**: `ssh -i ~/.ssh/doravo_deploy ...` đứng sau `&&` trong git-bash đôi khi fail `hostname contains invalid characters` (MSYS mangle). Dùng `-i "$HOME/.ssh/doravo_deploy"` là an toàn.
- **Python/heredoc qua ssh git-bash dễ vỡ quote**: lệnh lồng quote (`\"` + heredoc/base64) qua `ssh '...'` từ git-bash fail ngẫu nhiên (`unexpected EOF`, `KeyError` do mất quote — đã dính nhiều lần). Pattern ổn định đã verify: viết script local (`.sh`/`.py`) → `scp -i "$HOME/.ssh/doravo_deploy" <file> root@152.42.187.200:/tmp/` → ssh chạy → `rm -f` trên VPS. Dùng cho parse JSON API nguồn, parse HTML frontend (`ajaxs/client/load_products.php`), mọi logic python dài. Tránh dùng lại cùng pattern ssh+python trực tiếp sau khi fail 1 lần.
- **`rm -f` trong SSH command bị chặn chờ approval** (2026-08-16: dính 2 lần khi cleanup `/tmp/*.sh` + `rm -f /tmp/probe_xscr.php`): smart-approval flag lệnh chứa delete → nếu user vắng, lệnh timeout "BLOCKED" và toàn bộ probe mất. Giải pháp: bỏ `rm -f` khỏi command chính (bỏ qua cleanup / để `/tmp` tự dọn), hoặc tách cleanup thành lệnh riêng — KHÔNG để `rm` kéo theo cả probe. Với script chứa `rm` cuối file: scp lên xong ssh `bash /tmp/x.sh` KHÔNG kèm `rm -f /tmp/x.sh`; tự xoá sau (hoặc `rm` ở lệnh thứ 2 riêng biệt).
- **Crontab chứa key cron trong URL** — luôn mask khi dump: `crontab -l | sed -E 's/(key=)[^&[:space:]]+/\1REDACTED/g'`. Cron live: `cron/cron.php` mỗi phút, `cron/suppliers/*.php` mỗi 5 phút.
- **EOL khác nhau từng file**: live `cron/cron.php` CRLF, live `libs/stock_alert.php` mixed; local có thể LF/CRLF khác. Khi deploy, convert artifact về EOL của file live (đếm byte CRLF/LF bằng python) để diff sau deploy tối thiểu; PHP 7.4 không quan tâm EOL.
