# TikTok Video Upload Farm

Operate the TikTok video upload farm on the kibe PC (machines 1-80). Covers the canonical upload launcher, the video-pick thumbnail identity gate, the random render pipeline, and the resume/canary/audit discipline.

## When to use
- Running an upload batch: `run_tiktok_upload_batch.ps1 -Tik <N> ...`
- Fixing `VIDEO_PICK_TARGET_UNVERIFIED` / `POST_SUBMISSION_UNKNOWN` / `DUPLICATE_MEDIA_BLOCKED` / `POST_NEXT_SELECTOR_EXHAUSTED`
- Resuming a render or upload batch after a crash/reset
- Verifying a picker thumbnail really matches the pushed source video

## User's ground-truth preference: verify by LIVE PROFILE, one-off manual
Hard user correction (\"đánh dấu ngu rồi\") + explicit instruction (\"có hàm verify số video đã đăng mà chạy đi\", \"thao tác chụp này làm 1 lần thôi k cần ghi vào flow script\"): when deciding whether a machine already posted, the ONLY ground truth is the live phone profile — take a screenshot (or use `_count_profile_video_tiles_across_grid` / `_verify_profile_post_increment`) and look. The PC-side ledger (media-fingerprints, post-attempts receipts) can be wrong. Do this verification ONCE, manually, as a decision aid — do NOT bake a screenshot-verify step into the upload flow script. When a fact conflicts with what you assumed (e.g. profile empty despite ledger `verified_success`), the live screen wins; say plainly you were wrong rather than re-deriving a story from the ledger.

## Hard rules (learned the hard way)
0. **Parse \"k chạy <máy> <thời-gian>\" as EXCLUDE-one-machine, not STOP-everything.** Hard user correction (\"đọc ngáo vãi cặc\"): \"k chạy 38 phiên này thôi\" means only \"don't run machine 38 this session\" — ALL other work continues normally. The agent read it as \"don't run anything this session\" and froze the whole operation; the user had to clarify with profanity. When the user names a specific machine with a time qualifier, the machine is excluded from manifests; the rest of the batch plan proceeds unchanged. (Same shape as rule #7's off-limits machines.) Corollary: when in doubt about scope of a \"k ... thôi\" instruction, ask a ONE-LINE confirmation rather than stopping all work — but the default reading is narrow-exclusion. Always `run_tiktok_upload_batch.ps1 -Tik N -MaxParallel 16 -HostConfigPath D:/Taadaa/machine-config/kibe.yaml`. Do NOT hand-roll runners, xargs, or `bash -lc`. All Tik1/Tik2/TikN go through it.
2. **Resume, don't restart.** Batch launchers skip existing ffprobe-valid files. When a job dies (reset, power loss, exit 127), re-run the SAME command with `-ResumeVerifyExisting` and/or `-StartMachine <next>`. It continues — it does NOT overwrite. Never nuke output folders.
3. **Don't re-invent a working entrypoint.** If a command ran successfully before, run it EXACTLY again (add only the resume switch). Do not switch to a different script that demands a different workbook schema — e.g. `tik3_multi_batch.py` needs a `sttvideo` column that `tik3.xlsx` lacks, so it errors, while the original `run_tik3_random_render.ps1 -StartMachine 1 -EndMachine 80 -Parallel 1 -AutoRun` worked. Re-inventing entrypoints wastes a cycle and can clobber output.
4. **Independent streams.** Tik3 render and Tik2 upload are unrelated. Never block or ask about one because of the other; run them in parallel. Don't ask redundant clarifying questions when the answer is already in context.
5. **Audit gate before commit/push/live (user hard rule).** After completing ANY implementation phase — even a focused bug fix — dispatch the independent reviewer (see `requesting-code-review`) BEFORE commit/push/live-run. Skipping it is a hard violation; the user expects REJECT→fix→re-audit until `passed:true`. Concretely: a Tik2 video-pick fix was REJECTED round 1 for (1) returning the correlation-winning candidate instead of the histogram-winning one (would tap the wrong tile) and (2) a color-only metric that false-positives on same-color different-content thumbnails. Encode as invariants: the returned/tapped candidate MUST be the one the accepted metric selected; when a metric discards spatial info, require a structural/spatial guard + same-candidate agreement. Before risky changes, `git stash` (or tag) a revert baseline. APPROVED audit → commit/push → small live canary.
6. **Live canary before full batch.** After a fix + audit APPROVED, run 3 machines that previously exhibited the failure (e.g. 38/45/52 for video-pick) before the 80-machine run. The earlier conclusion that "AssignmentError persisted even with a complete manifest → registration gate is opaque" was WRONG — the manifest lacked `reviewed_at` and/or `-WorkerId` didn't match `owner_id`. Known-good one-machine recipe: manifest `{schema_version:1, assignment_id, owner_id, resources:["machine:35"], reviewed_at:"2026-08-14T10:15:00.000000"}` + `-WorkerId <owner_id>`. ## Video-pick thumbnail identity (the core fix)
Picker thumbnails for Tik2 script-render videos fail grayscale-64x64 correlation (~0.09-0.14 vs 0.35 threshold) because TikTok crops to 1:1, overlays a duration badge + emoji sticker, and re-compresses; the source frame is 9:16. Fix: keep frames RGB and add a color-histogram fallback + a 2x2 spatial-histogram guard. Exact measured values and thresholds are in `references/video-pick-identity.md`. Key gotchas: (a) the returned/tapped candidate must be the one the *accepted* metric selected (a bug returned the correlation winner even on the histogram path → wrong tile); (b) color-only histograms false-positive on same-color different-content thumbnails, so require the spatial histogram to agree on the SAME candidate.

### Threshold-margin case: CORRECT tile, all metrics just under threshold (2026-08-14, machine 7/8)
Deep investigation of `VIDEO_PICK_TARGET_UNVERIFIED` on machines 7/8: the pushed video was **provably correct** (extracted frame 1:1 matched the picker tile — a white Ford convertible with red interior, both frame and tile) and the MediaStore index was right (picker showed the single just-pushed video under "Gần đây"), yet verification failed. Workflow log showed `corr=0.243/None; hist=0.772/None; spatial=0.614/None` — **all three metrics under threshold (corr 0.40, hist 0.80, spatial 0.71) but histogram/spatial only slightly under** (hist misses 0.80 by 0.03; spatial misses 0.71 by 0.10). This is a threshold-margin problem on overlay/compressed tiles, NOT a wrong-push problem. **Before loosening thresholds, measure the NEGATIVE** (the same tile vs a different video from another machine's folder): only loosen if the negative sits clearly below (gap ≥ ~0.15) — a color-only loosening without spatial margin re-opens the false-positive class the audit rejected. Read the metrics from the workflow ERROR log line — do NOT re-derive them by comparing `video-pick-target-verify.png` against a source frame: that artifact is a FULL-SCREEN 1080x1920 capture (tile occupies a small corner region), so naive full-image correlation/histogram gives garbage (~0.14-0.16 even for the correct video — measured). The workflow's logged corr/hist/spatial values are computed with correct tile bounds from the UI XML and are the trustworthy numbers.

### RESOLUTION — COMPAT-VIDEO-PICK-002: single tile → tap directly, skip identity verification (user-driven, 2026-08-14)
The user cut through the whole verification debate: **"t tưởng cứ up media vào lượt nào đăng lượt đó xong xoá là xong mà"** — the flow is push media → picker shows ONLY the just-pushed video (gallery cleaned before push) → tap that one tile → post → delete. When the picker holds exactly ONE tile, identity verification (corr/hist/spatial) is pointless — there is no other choice to mistake it for. **Do not over-engineer verification when the cleaned gallery leaves a single candidate.** Implemented in `_handle_video_pick`: `if candidates and len(candidates) == 1 → tap directly` (log `[VIDEO_PICK] Single tile candidate; media cleaned before push, tap directly`); only MULTI-candidate pickers run `_verify_video_tile_identity` (keeps the fail-closed guarantee where ambiguity is real). Tests: existing fail-closed test (source frames unavailable) was made 2-tile so it still exercises the verify path; new `test_video_pick_single_tile_taps_without_identity_verify` asserts the single tile (center (182,535)) is tapped with NO identity verify (25 video_pick tests pass). Threshold loosening was NOT needed — the single-tile shortcut made the threshold-margin investigation moot. Full measured values + investigation gotchas: `references/video-pick-single-tile.md`.

## Pitfalls
- `pkill -f ffmpeg` / `pkill -f random_batch_render.py` before launching a fresh render to avoid two instances clobbering the same output folders.
- The launcher-generated `config-machine-N.yaml` may point at the wrong workbook (e.g. a stale Tik1.xlsx); the launcher regenerates the correct Tik2 config when invoked with `-Tik 2`. Don't run the module directly with a stale config.
- `git status` often shows pre-existing unrelated dirty changes (e.g. stale-lock reconciliation) in the same files you edited — scope your commits/audits to the phase you actually changed; don't let an unrelated dirty diff fail your audit.
- Tik2 source = random-script render; Tik1 source = "ông A" render. That difference alone explains why Tik1 passes video-pick and Tik2 fails correlation — it is NOT an ADB/machine fault.
- **Batch result `SKIPPED_LOCKED` en masse (e.g. 75/80) is NOT stale locks — it's cross-project contention.** When the `tiktok-luot nuoi acc` feed-session is running, it holds ALL machine locks (`project: tiktok-luot nuoi acc`, status `queued_v2`/`running`, `owner_active: True`). Upload cannot acquire any machine until feed releases. Diagnose by reading `C:\Users\Kibe\.codex\device-locks\machine_*.lock.json`: check `owner_active` AND the CURRENT owner PID liveness. **Re-scan before concluding stale** — the feed reservation phase rotates PIDs, so one scan may show a dead PID (stale-looking) while the live phase already owns a new PID; a second scan + `owner_active: True` + alive PID means the lock is legit and must NOT be force-released. Never force-release another project's locks (use that project's own release script, which itself fails closed on `queued_v2`/`running`).
- **Upload launcher has an interactive confirm.** `run_tiktok_upload_batch.ps1` blocks on a `Read-Host` "RUN" prompt. In background runs pipe it: `echo RUN | powershell.exe -NoProfile -ExecutionPolicy Bypass -File run_tiktok_upload_batch.ps1 ...`. `-AutoRun` is a Tik3-render-launcher switch, NOT an upload-launcher switch — passing it still leaves the prompt, then the process exits "Đã hủy vì chưa nhập đúng RUN".
- **`-AssignmentManifest` + `-WorkerId` — the manifest schema is fully known (read from `automation_core.assignments.AssignmentManifest`, 2026-08-14):** required fields `schema_version`(=1), `assignment_id`, `owner_id`, `resources` (`["machine:N"]`), **and `reviewed_at` (ISO string)**. `assert_owner` = casefold string compare; `-WorkerId` MUST equal `owner_id`. Failure modes: missing `reviewed_at` → `ASSIGNMENT_REQUIRED_FIELD_MISSING`; `-WorkerId` ≠ `owner_id` → `ASSIGNMENT_WRONG_OWNER`. Both are easy to fix — there is NO hidden worker-registration gate. See rule #6 for the known-good one-machine recipe.
- **Do NOT attribute a Tik3 (local ffmpeg render) failure to Tik2 (ADB upload) resource contention — or to any contention at all — without evidence.** Hard user correction: speculating "tranh tài nguyên" for a Tik3 `exit 127` was wrong; Tik3 render is CPU/local only and shares nothing with Tik2's ADB path (rule #4). When a process dies (exit 127/1), inspect the actual launcher log + running processes FIRST; don't narrate a theory. **A failure that looks "positioned" at one machine is usually transient** (process killed mid-run / machine reset), not a broken source: a Tik3 `exit 127` recurred at machine 27 twice but the 3rd resume passed machine 27 cleanly. Resume past the failed machine before deep-diving into its source folder.
- **NEVER restart the adb server while the farm/mirroring software is connected.** Hard user correction (`"con chó nào vừa restart adb vậy?"`): `taskkill //F //IM adb.exe; adb start-server` severs the mirroring software's (数云安卓投屏/数控安卓投屏) per-device connections — screens go "Điện thoại đã ngắt kết nối" en masse and the user must reset the PC to restore. A single device giving 0-byte screencaps is NOT grounds for a server restart; check `adb devices` for the serial, and if a device is mid-reconnect just wait. If a server restart is truly unavoidable, tell the user FIRST — never do it silently in a live farm.
- **When the user questions a gate/behavior ("sao m chế ra cái gate đó"), trace its git origin before defending or loosening it.** `git log -S "GATE_TAG" -- scripts/.../state_machine.py` shows the introducing commit + date; cross-check that date against the "working" batch date (`ls -dt batch-runs/batch_tik1*`). This separates a gate with a real incident behind it (keep fail-closed) from one worth reopening. COMPAT-POST-VERIFY-004 (commit `720dcd5`, 2026-08-12) was justified by a REAL false-positive: machine 74 verifier counted 1 viewport (3->4 fake) -> SUCCESS false -> workbook ghi 7 -> reverted to 6. Tik1 "ổn định" only because its batches ran 2026-08-10, BEFORE the gate landed — NOT because Tik1 video differs. Re-opening the gate is a real fix candidate, but never hand-wave it away as "self-invented".

## Post-histogram residual — REAL root cause is Post-button occlusion + receipt deadlock (NOT PROOF timing)
Once VIDEO_PICK passes live (machine 37: corr 0.357 / hist 0.759 / spatial 0.690 → pick completed; histogram path verified live at 0.855/0.781 on machines 50/34), every machine still ended `POST_SUBMISSION_UNKNOWN` (exit=2, MANUAL_REVIEW, 0 verified-success). Two stacked causes, in investigation order:

1. **Post-attempt receipt deadlock (look first).** `D:\CodexRuntime\tiktok-video\idempotency\post-attempts\machine_N_video_M.json` is the PC-side idempotency file (NOT the TikTok draft — draft lives inside the app). A receipt with `post_tapped_at` but no ACCEPTED (from an earlier failed turn) makes every later run log `Post tap already recorded... refusing to tap again` → machine never actually taps Post → VERIFY_POST UNKNOWN forever. Receipt ≠ draft; receipts sit on PC, drafts sit in TikTok. **Cleanup rule: delete only non-ACCEPTED receipts** (`post_submission_state != "ACCEPTED"`) so machines re-tap for real; keep ACCEPTED ones to avoid duplicate posts. 312 deleted / 360 kept on one pass.
2. **Hashtag-suggestion panel hides the Post button → `POST_NEXT_SELECTOR_EXHAUSTED`.** After caption paste the composer keeps the hashtag-suggestion panel open while the caption field still has focus → the Post button (top-right) is hidden. **`KEYCODE_BACK` is WRONG here** — on this TikTok build Back does NOT close the keyboard; it opens the hashtag-suggestion screen and the Post button disappears entirely (proven by same-device before/after screenshots). Never use Back to dismiss the panel. **The first preview-tap fix (`_post_composer_preview_point`, COMPAT-CAPTION-008) was REVERTED** — on live machines it dropped the keyboard/composer state and the Post button vanished too; and an unproven coordinate tap is fragile. **Concrete live failure signature (machine 5, 2026-08-14):** log ends `Looking for Next button... → Next button not found via semantic selectors → [POST_NEXT_SELECTOR_EXHAUSTED] POST: final composer/editor Next surface was not confirmed` (exit=1).
