# Evidence-First Delivery

Use this class-level workflow whenever a task produces visual/UI/farm/browser evidence that will be shown to a user. The goal is not merely to attach a file; it is to prove that the artifact is the correct, fresh, legible evidence and that the assistant actually inspected it before delivery.

## Core contract

- **Pre-send Vision Inspection**: See `references/pre-send-vision-inspection-and-anti-blind-delivery.md` for mandatory inspection via `browser_vision` or WinRT OCR prior to sending `MEDIA:<path>`.
- **Multi-Machine Gate 6 & Anti-Cheating**: See `references/multi-machine-gate-6-media-completeness-and-anti-cheating-20261021.md` for N-of-N media completeness in batch operations, per-machine serial binding, dual hash (SHA-256/pHash) anti-cheating, and zero-whining by structure.
- **Gate Conflict Resolution (Anti-Deadlock)**: See `references/gate-conflict-resolution-and-device-lock-screencap-wrapper-20261020.md` for resolving conflicts between Gate 6 (Media required) and Guard Device Bulkhead via `with_device_lock.py` instead of explaining away.
- **Anti-Context Inertia & Proactive Tool Delivery**: When user sends direct instructions with media (e.g. order management), prioritize literal prompt over conversational inertia; never substitute theoretical prose ("nói mõm") for working scripts and artifacts. See `references/tiktok-shop-farm-order-management-and-hub-pickup-tracking.md`.
- **Browser Vision Failure & Claude Vision Fallback**: See `references/browser-vision-daemon-failure-and-claude-worker-fallback.md` when `browser_vision` hits daemon conflict/interrupted errors — fallback to `claude_worker.py --role reviewer` with `[MANDATORY SIGHT]` prompt and strict anti-paralysis timeout rules.
- **Web UI Gate 6 Exemption Leak & Selector vs Banner Binding (Zero-Waiting-State FSM)**: See `references/web-ui-gate6-exemption-leak-and-selector-binding-20261020.md` for post-incident analysis on the regex exemption leak for web/browser tasks in egress guard, why hero/demo H1 banners must never be cited as active model status, and the 4-layer Zero-Waiting-State FSM preventing coordinator paralysis while enforcing physical evidence.
- **Informational Triage vs UI Mutation**: See `references/conversational-status-vs-ui-action-gate.md`. Gate 6 media verification applies strictly to UI/device mutation actions. Read-only explanation, log analysis, and database triage turns are exempt from media-attachment requirements and must not trigger output interception blocks.
- **Physical Canary Gate & Dual-Checkpoint Visual Evidence**: See `references/physical-canary-gate-and-dual-checkpoint-visual-evidence.md` for mandatory device-locked live canary on physical devices, avoiding the "mock test passed = done" trap, and dual pre/post vision verification.
1. **Do not claim success from summaries alone.** Runner exit code, `verified=True`, worker self-report, a database flag, or a path printed in a log is not visual proof.
2. **Deliverable vs upstream source distinction.** When proving that a service, server, API, or transformation pipeline works, the visual artifact MUST capture the DELIVERABLE itself (the API response, the rendered app, the consumer UI). NEVER substitute a screenshot of an upstream data source (e.g. a website being scraped, a database file on disk, or a raw log directory) as proof of the downstream deliverable.
2. **Read before sending.** Before emitting any `MEDIA:<absolute_path>` token, open the exact image with `browser_vision` (or use WinRT OCR when vision is unavailable) and inspect it. Confirm:
   - the correct app/screen/action;
   - the correct account, device, or target;
   - the expected new state;
   - no Home/Launcher/lock screen, black/dozing capture, popup obstruction, clipping, stale content, or unreadable text.
   - **Invariant LLM Soi Mắt Đọc Ảnh Trực Tiếp & Cấm Bịa Đặt Mô Tả (Anti-Confabulation & LLM Vision Soi Mắt Invariant - 2026-10-18):**

     * **Quy tắc BẮT BUỘC**:
       1. **In-Stream Capture Only**: Bằng chứng Canary BẮT BUỘC phải do chính runner chụp trong lúc app đang chạy tại đúng màn hình đích (Profile, Switcher, Following list). CẤM TUYỆT ĐỐI chụp fallback sau khi app đã thoát hoặc crash về Launcher.

Nếu phát hiện $\ge 2$ token hệ thống thuộc màn hình Home (*"Danh bạ", "Cài đặt", "Tin nhắn", "Photos", "Cửa hàng Play", "Launcher", "Điện thoại"*) ➔ **VETO NGAY LẬP TỨC**, hủy bỏ receipt, đánh dấu `CANARY_REJECTED`, cấm xuất bản thẻ `MEDIA:`.
       3. **Bản Thống Nhất Cơ Giới Hóa 3 Bên (Claude - Sol - Coordinator)**: Sửa code 100% qua Single Dispatch Gateway (`dispatch_worker.py`), cấm `delegate_task` sửa code, entrypoint canary duy nhất `canary_runner.py` đối chiếu scope `single` vs `wide` ($\ge 3$ máy), và chặn phản xạ khóc lóc/đùn việc khi bị Guard chặn.
   - **Chống Bẫy Lệch App Nền & Ảo Giác Báo Cáo Láo Khi Screencap Android (Target App Drift & Hallucinatory Screencap Trap - 2026-10-13):**

Đéo trị đc bệnh báo cáo láo của mày phải k, t nhớ t ép gate mày phải tự coi hình trc khi báo cáo r mà"*.

     * **Quy tắc BẮT BUỘC (3-Step Assertion Gate Trước Khi Nghiệm Thu Android)**:
       1. **Foreground Focus Assertion**: Trước khi screencap nghiệm thu, BẮT BUỘC kiểm tra `dumpsys window windows | grep mCurrentFocus` (hoặc `dumpsys activity top`). Focus BẮT BUỘC phải là đúng package đích (ví dụ TikTok `com.ss.android.ugc.trill`). Nếu focus là `LauncherActivity`, `SBrowserMainActivity`, hay app hệ thống khác ➔ CẤM screencap nghiệm thu, BẮT BUỘC đưa app đích lên foreground trước.
       2. **Mechanical WinRT OCR Token Verification**: Chạy WinRT OCR (`ocr_boxes.ps1`) lên ảnh screencap và assert tối thiểu 2 token độc quyền của màn hình đích (ví dụ Profile: `@<username>`, `"Đã follow"`, `"Hồ sơ"`). Nếu xuất hiện token của app ngoài (`google.com`, `"Đánh dấu"`, `"Tab"`, `"Tìm kiếm"` browser) ➔ VETO NGAY LẬP TỨC, khóa xuất bản, cấm gửi thẻ `MEDIA:`.

## Artifact selection and integrity

- Bind evidence to the exact run, machine/serial, account, attempt, and timestamp. Do not substitute a later screenshot, another machine’s artifact, a launcher screenshot, or an image from a different retry.
- Prefer the canonical runner artifact (`avatar-uploaded-confirmed.png`, matching `ui.xml`, `summary.txt`, `report.json`) over ad-hoc screenshots.
- Validate file existence, freshness, readable image structure, minimum size, and allowed artifact roots. Reject missing, stale, undersized, corrupt, black, white/solid-color, or out-of-scope files.
- For multi-step flows, preserve capture-before-teardown: screenshot and readback first, then HOME/force-stop/cleanup.
- When retrying a failed send, use a cache-busting filename and changed byte stream; do not rely on Telegram reusing a path/file ID.

## Failure handling

- If vision/OCR cannot inspect the exact artifact, report `UNPROVEN` or `INSUFFICIENT EVIDENCE`; do not attach it “for completeness”.
- If the mechanical gate rejects delivery, preserve the rejection reason and structured event. Fix the evidence or the delivery contract; never bypass the gate by moving the path into prose, a code block, or a second text message.
- Do not loop silently. A failed UI attempt requires an immediate error checkpoint; after three consecutive failures on one account/device, stop that UI loop and report the evidence-backed blocker.
- Separate observed facts from hypotheses. Quote OCR/log text when diagnosing a screenshot; do not invent a root cause from an exit code.

## Closeout and review

For code changes implementing evidence delivery, run focused offline tests and then the canonical closeout reviewer with the exact target-file allowlist. Do not use `--skip-test` when tests exist. If the reviewer rejects, remediate the exact findings (especially missing context enforcement, missing structured telemetry, or shallow delivery-flow coverage) and rerun until `APPROVED` with score >=85. Keep unrelated dirty files out of the candidate diff.

## User-facing style

The user prefers direct Vietnamese, concise status, and actual native images rather than folder links or path dumps. Lead with the result, then list only the evidence and blocker that change the decision. Never make the user ask “hình đâu?” after a UI operation.

## Avatar-only scope and false-policy refusal guard

When the requested mutation is only “đổi avatar”, bind the run to an **avatar-only scope lock**:

1. Do not change display name, username, bio, links, or any other profile field unless the user explicitly requests that field in the same task. A successful name edit is still a task failure if the user asked only for an avatar.
2. A generic model/tool refusal claiming that an ordinary avatar replacement violates policy is not an evidence-based platform blocker. Treat it as a transient refusal, state plainly that the refusal was incorrect, and continue only through the normal bounded UI flow after revalidating the live target.
3. Before every state-changing tap, verify the current app/activity, exact handle, and fresh screen capture. Never reuse coordinates from a stale screenshot after the device has drifted to Home, Messaging, another app, or another account.
4. Capture and verify the selected-photo checkpoint before tapping Next, then capture and verify the crop/confirmation checkpoint before Save, then reopen the exact Profile and verify the new non-placeholder avatar. Exit code 0, a successful ADB tap, a runner `verified=True`, or an old report image is not completion evidence.
5. If the final screen is unrelated, the avatar is unchanged, or the exact profile proof is missing, report `UNPROVEN`/`BLOCKED` and name the observed activity. Do not “repair” the report by mutating another profile field.
6. If an unrelated mutation already occurred, disclose it immediately as an out-of-scope side effect; do not bury it in implementation details or imply the avatar task succeeded.
