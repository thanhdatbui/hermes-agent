# Windows Ad-Hoc Verifier Harness Pitfalls

Use this reference when a verification reminder requires a temporary `hermes-verify-*.py` probe and the probe is generated by another launcher.

## Safe construction

1. Snapshot pre-existing `%TEMP%/hermes-verify-*.py` files; clean only files created by the current run.
2. Create the probe with `tempfile.mkstemp(prefix="hermes-verify-", suffix=".py", dir=tempfile.gettempdir())`.
3. If embedding source inside a launcher, use sentinel replacement such as `__REPO__` and `__PYTHON__`; do not use `.format(...)` or an f-string over source containing dictionary/set braces.
4. Convert injected Windows paths to `Path.as_posix()` before insertion. A generated ordinary Python string containing `C:\Users\...` can fail parsing because `\U` starts a Unicode escape.
5. Run the probe from the repository root with a fresh subprocess. Clear conflicting `PYTHONPATH` where needed and isolate `PYTHONPYCACHEPREFIX` in a temp directory.
6. Always remove the owned verifier and isolated pycache in `finally`, and print explicit existence checks.

## Failure classification

- `KeyError` from launcher formatting: harness-generation failure; repair interpolation.
- `SyntaxError` / `unicodeescape` in the generated probe: harness path-escaping failure; use POSIX paths or raw literals.
- Assertion/test failure after the probe starts: product or test evidence; investigate normally.
- Successful focused pytest output plus AST/seam assertion: report as **ad-hoc verification**, not full-suite green.

Keep setup failures separate from product results; never report a harness failure as evidence against the patch.
