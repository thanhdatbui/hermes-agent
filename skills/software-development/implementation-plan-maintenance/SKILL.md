# Implementation Plan Maintenance

Editing an EXISTING implementation plan, or authoring a NEW one PLAN-ONLY for a Taadaa multi-repo migration. Generic one-off plan authoring (non-Taadaa) remains the bundled `plan` skill; this skill owns the Taadaa PLAN-ONLY protocol (safe-boundary grounding + verification report) that the generic skill does not carry. Typical maintenance jobs: applying residual audit rounds (NIT/MINOR/MAJOR findings) to phase/step sections, completing test skeletons that still contain `...`, and making plan code blocks copy-paste-correct against the repo they target — without touching repo code.

## Trigger conditions
- User references an audit on a plan doc: "residual audit vòng 2", "sửa plan theo NIT/MINOR/MAJOR", "trả danh sách thay đổi theo locator".
- Plan contains test skeletons with `...` bodies that must become concrete arrange/act/assert.
- User asks to verify/ground plan code blocks against the real source repo (plan-only edits allowed).
- User asks to AUTHOR a new plan PLAN-ONLY: "lập implementation plan PLAN-ONLY thật trong repo X", "chỉ tạo đúng file `.hermes/plans/<YYYY-MM-DD>_<slug>.md`", multi-repo migration/rollout plans ("nối N consumer vào core đã ship", "migrate X sang Y"). When the task names an EXACT filename, use it verbatim — do not substitute the generic timestamp convention.

## Authoring a NEW plan — Taadaa PLAN-ONLY protocol (multi-repo / phased)

Use for "PLAN-ONLY, chỉ tạo đúng file plan, không sửa source/test/config/consumer, không commit, không live" tasks in Taadaa repos. The deliverable is ONE markdown file under `.hermes/plans/`; the final reply reports path + line count + SHA-256 + phase count + matrix count (user-mandated format, see end of this section).

1. **Governance chain first (read-only).** `D:\Taadaa\AGENTS.md` (audit ladder: AG Opus primary, GPT review, opencode-audit; one audit slot per plan/diff; worker = fresh session-model flash/Luna, Terra/Sol read-only) → repo `AGENTS.md` → `docs/ai/*-development-guide.md` → `docs/scope.md` → prior phase reports ("đã ship" baseline, e.g. a Phase 4 audit report). Quote the HEAD/base commit and the "already shipped" capabilities as FACT in the plan header.
2. **Baseline verification with git (never assume).** `git -C "<D:/Taadaa/...>" rev-parse HEAD`, `git status --short --untracked-files=all`, `git log --oneline -N`, per-consumer pin files (`requirements-automation-core.txt`, `pyproject.toml`), `ls dist/` wheel list. Pins are HETEROGENEOUS and may sit BELOW the audited baseline (one consumer pinned 0.4.18 while scope.md targeted 0.4.25) — verify every pin file individually and record the discrepancy as a FACT/gap.
3. **Safe-boundary grounding (hard rule).** Never read: `.env*`, any filename containing `secret/credential/token/password/passwd/auth/session/otp/serial`, workbook data (`.xlsx/.xls/.xlsm/.csv`), logs/raw artifacts (`.log/.jsonl/.ndjson`, `.ai-runs`, `.runtime`, outputs/runs/reports/data/assets), `.online_serials.txt`, `.gemphonefarm`, `node_modules`, `__pycache__`, `.bak/.pyc`. For excluded files record ONLY path + status. Every symbol written into the plan must be grounded path:line (read_file snippets); search_files/rg dies on Windows drive-letter + Vietnamese/diacritic paths (`os error 3`) — use terminal grep or plain read_file.
4. **Evidence classification (user-mandated).** Label every claim `FACT` (read path:line), `NOT_FOUND` (scanned, absent), `NOT_INSPECTED` (boundary-excluded), `NEEDS_PROOF` (doc/AGENTS says it but safe code lacks evidence — e.g. "guided recovery" with no symbol, or registry existing but no live call-site). Static code is NEVER live proof. Consumer with no verified runtime call-site → its phase starts with a dedicated discovery phase, or is marked NEEDS_PROOF and STOPPED — never invent a patch point.
5. **Plan skeleton (user's 11-point checklist, condensed).** (a) mandatory invariants table (core app-neutral; consumer adapter owns mapping; no `pm clear`; no live validation; artifact-backed recapture+verifier; owner lease; no-splice; cap never reset; AI permission scoped/bounded/audited; no-hook/fail ⇒ FAILED_LOCKED); (b) topology migration — shared adapter contract in core is INTERFACE-ONLY (Protocol/dataclass empty of policy), each consumer adapter registers strict `RecoveryHandlerSpec` + `EscalationHook`, maps local failure taxonomy, invokes the REAL runtime path, preserves existing flow until the verifier gate, no second scheduler/retry loop; (c) sequential phases, ONE worker/worktree ownership per phase, pilot-first (pick the consumer with the most code evidence — e.g. the one already using the registry), no parallel on the same component; (d) per-consumer row: repo path, safe files/symbols verified, current pin → target wheel/version, adapter insertion point, failure-class mapping, retry/budget mapping, recapture/verifier seam, lock-ownership seam, RED→GREEN tests, acceptance/gate audit, rollback; (e) core package distribution: bump + build wheel FIRST, update consumer pins ONLY after compatible wheel + focused tests, `PYTHONPATH=src` for core tests, never let tests resolve the installed site-packages copy; (f) preflight per phase: snapshot dirty state, dedicated worktree/branch from a clean base, preserve unrelated dirt, no credential/workbook/log reads, no live; (g) shared test matrix (no-hook, missing/incomplete handler, HARD_STOP, NON_RETRYABLE, generic exception, budget exhausted, verifier failure, lock retained, restart/re-fire, redaction, no implicit recovery) + consumer-specific suites; (h) stop conditions (NEEDS_PROOF ⇒ stop that consumer, no fake green; 2 rejected audit cycles on the same invariant ⇒ consolidated design audit) ; (i) each phase lists files allowlist, forbidden paths, RED/GREEN commands, expected evidence, commit message, independent audit gate, rollback; (j) final acceptance (all adapters registered + runtime-connected, pins consistent, focused tests, no dirty file overwritten, final report).
6. **Final verification report (user-mandated format — do not skip).** After writing: read/stat/hash the file back (`wc -l`, `sha256sum`), confirm `git status` shows ONLY the new plan file untracked, NO commit. Reply with: absolute path, line count, SHA256, phase count, consumer-matrix count. Never fabricate any of these numbers ("không bịa") — if a count was not computed, say so.

## Golden rules
1. **Respect scope exactly.** "KHÔNG sửa code repo" = touch ONLY the plan .md; read repo files freely (read_file), edit nothing else. State the boundary in the final report.
2. **Artifact existence is a hard gate.** A planner/worker summary saying "written", "created", or "verified" is not evidence. Before auditing or reporting completion, independently read/stat the exact plan path, confirm nonzero size and expected markers, and record the actual line count/hash when the artifact is important. If the path is absent, stop at `BLOCKED/UNKNOWN`; do not audit a nonexistent plan or dispatch implementation.
3. **Report changes BY LOCATOR** (user preference). Final summary = one bullet per change: `Phase X Step Y — what changed` with line ranges / section IDs; end with file path + line-count delta. Not prose paragraphs.
3. **Zero `...` placeholders in test bodies.** Every test gets full arrange (existing fixture helpers) / act (call under test) / assert (exact value, or exception + exact ReasonCode). Placeholder skeletons are audit findings (NIT B-class) — plans must be implementable by workers with zero guessing.
4. **Plan code = ground truth for workers.** Before writing any code block into the plan, verify signatures, imports, AND the actual dict/record field keys against the real repo (read_file the modules). Verify callable ownership too: distinguish a module-level function from a class method, bound method, property, or Protocol member; do not turn `Class.method` into `from module import method`. A wrong signature, wrong ownership level, OR a missing key (`e["seed"]` when entries carry no seed key) ships a bug into the plan itself before implementation starts.
   - Before accepting an implementation commit, execute every plan-specific import/smoke command against the exact worktree or extracted wheel. The smoke must import the owning class when the API is a method and assert the shape with `getattr` (for example, `callable(getattr(RecoveryQueue, "finalize_failed_locked", None))`), while asserting provenance is the intended worktree/extract directory rather than installed `site-packages`.
   - If execution exposes a wrong API shape in the plan, stop the implementation gate. Patch the plan only, re-read/hash it, and re-audit the revised plan; do not add a production alias or move a method merely to satisfy stale plan text.
5. **Keep audit finding IDs in code comments** (`# NIT A.2: ...`, `# MINOR 4: ...`) so test → finding traceability survives into the repo code.
   - Before allowing an implementation commit, execute every plan-specific smoke/import command against the exact worktree or extracted artifact. An audit `APPROVED` is not evidence that a command is executable. If a planned command fails because the plan used a wrong API shape, stop the implementation gate, patch the plan only, re-audit the updated plan, then rerun the worker verification.
5. **Keep audit finding IDs in code comments AND plan prose** (`# NIT A.2: ...`, `# MINOR 4: ...`, and in plan text `(MINOR 4.4: ...)`) so test → finding and plan-sentence → finding traceability survives into the repo code and the next audit round.
6. **Layered-validation tests pin the layer.** To prove rejection at layer N (e.g. block-level), the injected value must PASS all earlier layers — recompute valid IDs with the formula (`entry_id_for(...)`, `block_id_for(...)`) instead of injecting junk, and assert the exact ReasonCode (`excinfo.value.args[0] == "MANIFEST_IDENTITY_MISMATCH"`) so the test proves WHICH layer rejected. Contrast test pairing: junk-id test proves entry-level rejection; re-hashed-id test proves block-level rejection.

## Plan revision integrity and runtime-grounding gates

0. **MAINTENANCE BASELINE-DRIFT PRE-FLIGHT (before trusting the plan's own stated baseline).** When you REVISE an existing plan, its claimed HEAD SHA, file SHAs, and "test X is missing / module Y is new" come from the parent's memory and may be STALE against the live repo — commits land, tests get re-landed via cherry-pick, file bytes change. Run before patching: (1) `git rev-parse HEAD` + `git branch --show-current`; (2) `git status --short --untracked-files=all` to snapshot foreign dirt and confirm untracked-draft preimage SHAs still match the plan's recorded values; (3) `sha256sum` the plan's claimed file hashes vs live; (4) AST-scan `python_runner/tests/*.py` for every `module::test_node` the plan references or claims is missing — a "missing" claim MUST be verified by scan, never by belief (use `references/scan_plan_test_nodes.py`); (5) `git log --oneline -- <file>` to see whether a "rolled-back / non-evidence" commit was later re-landed. Re-ground the FACT table and task bodies to the CURRENT repo; never claim a test is missing when the scan shows it present, and never call a superseded rolled-back SHA "the only source" when a later cherry-pick re-landed the change. Full recipe in `references/plan-baseline-drift.md`.
1. **An audit verdict is bound to exact bytes, not a filename.** Record `path + SHA-256` in the audit prompt/report. Any edit after `APPROVED`—including typo cleanup, a corrected command, or an “informational” observation—invalidates that verdict. Re-read, re-hash, and re-audit the current file before implementation. Never report an earlier verdict as approval of a later revision.
7. **`patch` old_string/new_string is the literal content — never embed editorial instructions in new_string.** A serialized same-file patch batch where new_string contains meta-text like "Dòng 69 hiện là: … đổi thành: …" writes the instruction INTO the file and corrupts it. After every patch batch, re-read the modified region and re-hash the file before reporting; a stale/corrupted final SHA is worse than no SHA.
2. **A contradictory literal command is blocking even when nearby prose self-corrects it.** Workers copy command blocks. Examples: passing `.ps1` to `py_compile`, naming a nonexistent CLI verb, or listing a stale pytest node. Fix the executable block itself, rerun consistency scans, then re-audit; do not accept “the paragraph says not to do that” as closure.
   - **Shell contract is an invariant, not code-fence decoration.** If the plan declares Git-Bash, every copy-paste command must use POSIX continuation (`\\`) or one physical line. PowerShell backtick continuation remains invalid even when the fence is labelled `powershell`; invoke `powershell.exe` explicitly only for the PowerShell fragment. A plan that mixes an MSYS `/d/...` command with backticks is not executable from its declared context.
   - **RED/Verification node identity must match exactly.** Treat each pytest node as `(module, test_name)`, not merely `test_name`. If RED assigns `test_x` to `test_job_spec.py`, Verification must execute that exact node or the whole `test_job_spec.py` module—not `test_contract.py::test_x`. Explicitly label any future test node and ensure its allowlisted module is created before RED.
   - Run `python scripts/validate_plan_execution_contract.py <plan.md>` before every exact-hash audit. It blocks Git-Bash/PowerShell continuation mismatches and RED nodes omitted or invoked from a different module. Review its informational verification-only nodes; they are allowed only when intentional regression anchors.
3. **Ground state-changing CLI plans in both help and implementation semantics.** Verify the installed subcommand/flag, persisted state transition, and read-back shape. A verb name alone does not prove behavior: a manual “run” may reject paused jobs, an edit may preserve paused state, and create may persist an enabled job before the coordinator can pause it. Encode the real transition plus rollback/reconciliation tests, not an inferred workflow.
4. **Probe platform durability primitives before prescribing them.** POSIX recipes such as opening and `fsync`-ing a directory may be unsupported on Windows. Treat durability as `NEEDS_PROOF` until exercised on the target Python/OS; specify supported file flush + atomic replace/pointer publication and fault-injection tests rather than copying a POSIX sequence verbatim.
5. **Plan-only workers can still contaminate the worktree.** If any worker writes outside the exact plan allowlist, classify its result as outcome-unknown. First prove the writer is inactive, then stat/hash/diff the live files, preserve pre-existing user dirt, and revert/delete only artifacts attributable to that worker. Never race a live writer with `git restore`, and never advance to audit/build from a worker summary alone.
6. **Long-running work must be reconciled with scheduler timeout/overlap semantics.** A frequent cron tick plus a long child process requires an identity-bound reservation/lease, duplicate suppression, and explicit terminal ownership. Verify whether the scheduler waits, times out, or detaches; do not rely on a default timeout as lifecycle management, and do not make stale-lease reclamation silently retry live work.

## Workflow
0. **Continuation and worker-result gate.** If a prior session says a plan worker is "done", independently reconcile the exact artifact first: inspect active delegation/process state, stat/read the target plan, and compare its current content/hash against the claimed result. A worker timeout, upstream 503/504, `max_iterations`, or summary without a changed artifact is **not** completion. Do not advance to audit/build from a stale plan; re-dispatch only after exact-scope reconciliation proves the prior worker is inactive and made no usable change.
1. Read the plan fully (paginate big files with offset/limit; note total_lines). **RECONCILE the task's claimed defects against the ACTUAL on-disk file BEFORE editing.** A correction/maintenance task often describes the plan by a STALE snapshot (e.g. "the file has no Task 9 section / records old SHA `22a1fc333880` / is 55 KB"). The live `.md` may already be a NEWER corrected revision landed after that snapshot (larger byte count, later birth time, already carrying the section and current HEAD). Before applying any described patch, read/grep the real file and confirm each claimed defect ACTUALLY EXISTS. If every claimed correction is already present, perform READ-ONLY verification (re-read fully; check UTF-8 / byte count / SHA-256; confirm no stale SHA remains) and report "already satisfied — zero edits applied" — do NOT blindly re-apply the described patches (they either no-op confusingly or risk corrupting an already-correct artifact). Only edit where a genuine gap remains. This is a documentation-only correction discipline: never edit an artifact that is already compliant, and never claim you "fixed" something that needed no fix.
2. Locate placeholders / target sections. On Windows drive-letter paths — plain `D:\Taadaa\...` AND Vietnamese/diacritic paths (`D:\Taadaa\tiktok-luot nuoi acc`) — search_files/ripgrep FAILS (`os error 3`). First try terminal grep (cheapest), Python for scan logic:
   ```bash
   cd "/d/Taadaa/automation-core" && grep -n 'run_all\|1.69s' .hermes/plans/*.md   # symbol/leftover check
   cd "/d/Taadaa/tiktok-luot nuoi acc" && python - <<'PY'
   from pathlib import Path
   p = Path('target.md')
   for i, line in enumerate(p.read_text(encoding='utf-8').splitlines(), 1):
       if '...' in line:
           print(f'{i}|{line}')
   PY
   ```
   Classify each match: standalone `...` inside a code fence → MUST fill; legit signature notation (`entry_id_for(...)`, `sha256(...)`, `tuple[int, ...]`, `{None, ...}` frozensets) → leave, enumerate in the report as legitimate.
3. Ground tests in the real repo: read the modules under test — function signatures (incl. keyword-only args), required-field set constraints, exact dict keys, and the fixture helpers the plan already defines (`_fleet_pick`, `_fleet_source_raw`, `fleet_source()`, `seven_source()`, `FixedClock`, ...).
4. Patch with `patch` (replace mode, unique old_string + surrounding context). **Same-file edits MUST be serialized — one patch call per turn.** Parallel/batched `patch` calls on the SAME plan file race and lose updates; batch only edits across DIFFERENT files. Re-read modified regions afterwards to confirm code fences/indent survived.
5. **Findings that demand NEW design (not just skeleton fills)**: an audit finding like "MEDIUM: Phase 1 must NOT reuse `finalize_blocked` as-is — design `finalize_failed_locked`" or "Phase 2 hook coverage must list `recovery_runner.preflight`" requires editing MULTIPLE plan sections, not one code block. For each such finding, touch ALL of: **Files** list (add the module + real symbol names), **RED tests** (add numbered R-tests covering the finding's edge cases), **GREEN/implementation guidance** (describe the new design, explicitly negate the banned approach), **Acceptance criteria**, and the **Gate audit** paragraph. After patching, grep for stale phrases the finding superseded (e.g. `grep -c 'tái sử dụng'`, `grep -c '1.69s'`) and confirm 0 remain — an old contradictory sentence left behind is an audit miss.
6. **Ground-truth audit-named symbols before writing them into the plan.** Audit findings may reference symbols that don't exist in the repo (e.g. a finding said `run_all` but `recovery_runner.py` only has `run`/`_run_one`; `grep -n '    def ' src/...` to confirm). Reference the REAL symbol and note the audit's alias (`audit gọi nhóm này là run_all`) so the worker doesn't chase a phantom method. Same for terminal-status sets (`_allowed`, `_TRANSITIONS` keys): grep the actual sets before claiming which transitions exist.
7. Re-scan for `...`; verify 0 standalone remaining; confirm line-count delta.
8. Report by locator with verification evidence (scan results, legitimate-match enumeration, size before/after).

### Applying a multi-finding audit round (NIT/MINOR_FIXES verdict, N findings on ONE plan file)

1. **Verify each finding against the real repo BEFORE writing plan text.** Audit locators can be stale or half-right (e.g. "RED on wheel 0.4.44 may be wrong"). Ground every artifact claim with a name-only scan: `unzip -l <wheel>.whl | grep -E '\.py$'` (no extract, no install, no site-packages) for wheel-content claims; `ls dist/` for artifact existence; `git status` for state claims. Record verified FACT, NOT_FOUND, or NOT_INSPECTED — never assert "wheel X lacks module Y" without the scan.
2. **Audit cites ONE locator; the stale wording usually repeats across the file.** Sweep the WHOLE plan for the phrase the finding supersedes (`grep -n 'Phase count: 12'`, `grep -n 'runtime-connected'`, `grep -n 'xác nhận lại'`) — goals (M1/M6), §13.6 stop conditions, risk section §14, and audit-gate paragraphs all echo it. Fix EVERY occurrence in one sweep; re-grep expecting 0 (or only intentional negations like `không để "xác nhận lại" mơ hồ`).
3. **Embed the finding ID in plan prose** (`MINOR 4.4: ...`, `MINOR 3.2 — ...`) right at the rewritten sentence — a re-auditor greps for the ID, and workers see which sentence satisfies which finding. Extends golden rule 5 from code comments to plan text.
4. **Same-file edits serialized** (workflow step 4) — one `patch` call per turn for N findings on one file; re-read regions between edits.
5. **Close with the full verification cycle**: full paginated re-read, stale-scan greps = 0, `wc -l`, `sha256sum`, `git status` (only pre-existing untracked plans; no tracked modified), then report by locator with line-count delta.
6. **Evidence provenance is mandatory for newly inserted FACTs.** A command mentioned in an audit or an existing plan is not execution evidence. Run the exact command, capture its output in the current verification record, and only then write `FACT`/"đã chạy thật" prose. If output was not actually captured, write `NEEDS_PROOF` or `NOT_INSPECTED` and make the execution step obtain the evidence later. Never upgrade a remembered or claimed CLI-help result into a verified fact during a plan patch.
7. **Keep scope to confirmed findings.** Do not silently invent new audit IDs, acceptance semantics, or production design while repairing a MINOR round. If related hardening is necessary, label it explicitly as an audit mapping or `NEEDS_PROOF`, and do not claim it was part of the auditor's verified verdict.

## Pitfalls
- **search_files/rg dies on Windows drive-letter paths** (`The system cannot find the path specified (os error 3)`) — plain `D:\\Taadaa\\...` AND Vietnamese/diacritic paths. Workaround: terminal `grep -n` (POSIX `/d/...` paths) or the Python scanner above; the repo's own conventions often already say "mọi grep dùng terminal". Same class of failure: `git -C /d/Taadaa/...` can die with `fatal: cannot change to '/d/Taadaa/...'` while the identical path works as a terminal `workdir` — prefer setting `workdir` to the repo root and using plain relative `git status`/`git log` instead of `git -C <msys-path>`.
- **Native Windows `python3` does NOT resolve MSYS `/d/...` paths.** Terminal `read_file`/`grep`/`wc`/`sha256sum` work with POSIX `/d/Taadaa/...`, but `python3 -c "open('/d/Taadaa/...')"` raises `FileNotFoundError` (native CPython wants `D:\\Taadaa\\...`). For `python3` UTF-8/byte/hash checks, convert first with `cygpath -w "$F"` and pass the Windows path (e.g. `python3 -c "import codecs; codecs.open(r'$(cygpath -w "$F")', encoding='utf-8').read()"`). The Hermes `read_file` tool itself reads `/d/...` fine, so prefer `read_file` for content checks; reserve `python3`+`cygpath` only when you need a programmatic transform.
- **Wheel-content claims need a name-only scan, never assumption.** "Wheel X lacks module Y" (e.g. `escalation.py`) must be grounded by `unzip -l <wheel>.whl | grep -E '\.py$'` BEFORE writing a RED step or rationale — this is a safe-boundary-friendly read (no extract/install/site-packages). An audit saying "0.4.44 có thể đã chứa module" cuts BOTH ways: scan first, then assert verified FACT or record NOT_INSPECTED for wheels you can't locate (e.g. 0.4.24 absent from `dist/`). If the RED artifact doesn't exist at execution time, the plan step must pre-declare "ghi discovery/NOT_FOUND + NEEDS_PROOF, không fake RED".
- **Audit findings may name non-existent symbols** (phantom method `run_all` vs real `run`/`_run_one`). Grep the source before writing the plan reference; use the real symbol + note the audit alias. Chasing the phantom name ships a plan a worker cannot implement.
- **Policy/invariant sentences must not be weakened while applying findings.** The user's fail-closed policy ("mọi fail cuối/AI fail/no hook giữ lock FAILED_LOCKED vĩnh viễn; không retry/release tự động") stays untouched even when a finding adds detail — verify the plan still states the policy, only expand around it.
- **Timing is NOT an invariant.** Baseline expectations like `1 error in 1.69s` must be phrased `timing machine-dependent — audit ghi nhận 1.43s, không coi timing là invariant` (or drop the seconds entirely). Grep for the old number after patching; a hard-coded timing in a plan becomes a false verify failure on another machine.
- **`set(payload) == required` / `set(entry) == required` validation families** (manifest.py-style): adding any key — top-level (`blocks`, `maintenance`) or per-entry (`block_id`, `session_index`) — REQUIRES updating the required set in the same phase or every record fails validation. Removing/renaming keys breaks it the same way.
- **Strict equality checks cascade**: `payload["constraints"] == CONSTRAINTS` — any constants edit re-derives IDs/hashes → golden-vector tests must update exactly once at a single designated phase. Flag it as single-point in the plan.
- **JournalStore.append() auto-adds ONLY** `schema_version=2`, `terminal=False`, `manifest_id`, `manifest_sha256`, `manifest_path` — NO `timestamp`. Never assert `"timestamp" in event` in planned tests unless the plan explicitly adds that field (a planned test shipped with this bug; see references).
- **Formula args ≠ dict keys**: functions like `entry_id_for(..., seed)` take a value that is NOT necessarily a field on the entry dict — entries carry manifest-level seed, not a per-entry `seed` key. Use the payload-level value (`payload["seed"]`), not `e["seed"]`.
- **CRLF files**: Python scan output shows `\r`; strip before matching. `patch` handles CRLF fine; `git diff --check` CRLF warnings are OK.
- **Markdown table integrity after patching**: when replacing a table row, preserve exactly one leading `|` per row. A replacement that accidentally starts with `||` can silently corrupt the plan's rendered table even though the textual change is otherwise correct. Re-read the complete file (not only the edited excerpt) and inspect every changed table row before final verification.
- **Verification-contract blocker vs implementation defect**: if execution evidence shows an import/smoke failure but source locators prove the capability exists as a class method (for example, `class RecoveryQueue` at `:152` and `def finalize_failed_locked(...)` at `:581`), repair the plan's verification contract to import the owning class and assert `callable(getattr(Owner, "method", None))`. Do not move the method, add a module-level alias, or alter worker/source code merely to satisfy a stale smoke contract. Record the failed contract and the real evidence in the Phase Evidence and Audit gate wording.
- **Whole-plan stale scan with intentional negations**: scan exact stale imports and module-level wording across the entire plan after every related patch. Zero means zero executable/stated stale references; an explicit sentence saying the old contract is forbidden is intentional and should be reported separately, not mistaken for a stale hit.
- **Fixture lifetime assumptions**: tests that mutate shared state (journal FAILED → re-pick) depend on per-test fixtures (tmp_path-style). If the plan's fixture scope is unverified, flag the assumption in the report instead of silently relying on it.
- **Journal transition setup is part of the test contract**: an execution `FAILED` event cannot be appended to an empty stream; the transition matrix requires a valid launch lifecycle first. Ground plan snippets by either exercising `Runner` with a real failing path or constructing `LAUNCH_RESERVED → LAUNCH_STARTED → LAUNCH_FINISHED → FAILED` with a canonical `ExecutionReservationV2`. Never copy a direct `JournalStore.append("FAILED", ...)` snippet without checking the transition matrix.
- **Authoring: consumer repos carry pre-existing dirty state** (modified AGENTS.md/device_lock.py/tests, untracked files). Snapshot `git status --short --untracked-files=all` per consumer during preflight; the plan must commit to preserving it, and the final check compares the snapshot — a plan that writes to the consumer repo root instead of a dedicated worktree is a violation.
- **Authoring: heterogeneous core pins are the norm, not the exception.** One repo may pin a wheel BELOW the audited baseline while siblings pin above it; both `requirements-automation-core.txt` and `pyproject.toml` can carry pins that must stay consistent. Never state a single "all consumers are on X" line without reading each pin file.
- **Authoring: re-count phase and matrix numbers from the actual file** before reporting; a plan edited after writing invalidates earlier counts. The final reply requires absolute path, line count, SHA256, phase count, and matrix count — all computed, none guessed.
- **Wholesale-replace a stale plan with `write_file`, not `patch`/`append`.** When the task is "REWRITE the plan file wholesale / replace it, don't append", `write_file` overwrites the entire file in one shot — correct and safe. `patch` is for targeted edits; appending to a stale 200+ line plan leaves the old (wrong) content behind and is the wrong tool for a full rewrite. After `write_file`, re-read head/tail to confirm the NEW header/footer landed and the old content is gone.
- **`write_file` emits a "modified since you last read it" warning on plan files read earlier in the session — not an error, but re-verify.** For an exclusive-allowlist "rewrite DUY NHẤT one plan file" task, treat the on-disk file as untrusted after `write_file`: recompute SHA-256 / bytes / newline count via terminal (NOT the in-tool `bytes_written`), sweep stale tokens (should be 0), prove exclusive write scope with `git status --short --untracked-files=all` plus `git diff --name-only` (excluding pre-existing dirt — modified `HANDOFF.md`/`scripts/*` and pre-existing untracked drafts are NOT your edits), assert self-hash==0, and confirm required anchors (baseline HEAD, NON-EVIDENCE quarantine ref, `PENDING_AG_OPUS_REAUDIT`/`NO-LIVE` footer). Full recipe: `references/post-rewrite-verify-scope.md`. Do not `git add`/commit (plan-only).
- **Exclusive-scope proof must exclude pre-existing dirt, not hide it.** On a PLAN-ONLY rewrite, `git status` will list pre-existing modified files (` M HANDOFF.md`, ` M scripts/...`) and pre-existing untracked drafts — those were dirty before the task and are out of scope. The "only this file changed" verdict holds only after you pattern-exclude those paths and confirm none of them were touched by you. If an allowlisted source file or governance/HANDOFF file shows a change you did not intend, STOP — that is a scope violation.
- **Contaminated/non-authoritative `origin/master` needs a 9R authority-reconciliation gate, not a baseline-drift patch.** `plan-baseline-drift.md` covers STALE facts; it does NOT cover the case where local `HEAD` still matches the plan's claimed baseline but `origin/master` fast-forwarded ahead (merge-base == local HEAD) carrying unapproved implementation bytes, while a `quarantine/...` ref holds parallel provenance and a dangling object floats free. (1) Run a containment probe (`git merge-base --is-ancestor <sha> <ref>` for every suspect SHA × {HEAD, origin/master, quarantine ref}) before writing any ref fact — a commit can be an ancestor of BOTH origin AND quarantine (NOT "only in quarantine"), others only in quarantine, and a fourth dangling in NEITHER; never write "quarantine contains <sha>" for a dangling object. (2) Preserve provenance with NO deletion: pin a dangling object to a dedicated `refs/quarantine/<...>` ref and verify the existing quarantine ref still resolves + contains its expected commits; never delete a quarantine ref; `git cat-file -e <sha>` is the forensic reachability guard. (3) Forbid `reset --hard`/`checkout --`/`clean`/force-push/blind `pull`/`rebase`/`cherry-pick` of implementation commits — and do NOT cherry-pick policy-only commits whose ancestry includes the implementation commits. (4) Create an isolated clean authority branch (`git branch phase9-authority-<base> <base>`) proven to exclude every NON-EVIDENCE commit; local dirty main worktree stays untouched; build tasks run only on that branch. (5) Mark `origin/master` contaminated/non-authoritative → any push/merge to it is FINAL_BLOCKED until an explicit owner decision; inject a mandatory 9R gate (re-probe drift, preserve provenance, no forbidden mutation, isolated branch, AG exact-byte audit) before the first implementation phase (map into ordered task list, rollback table, stop conditions, acceptance matrix F-00). Full recipe + verified live example in `references/plan-authority-reconciliation.md`.
- **No-side-effect `git diff --check` recipe (PLAN-ONLY-safe).** You must prove the plan is clean, but you must NOT leave the index modified. Use intent-to-add so `git diff --check` / `--stat` exercise the same whitespace/conflict-marker gate a commit would, then reset it away:
  ```bash
  cd "/d/Taadaa/tiktok-luot nuoi acc"
  PLAN=".hermes/plans/<ts>-<slug>.md"
  readlink -f "$PLAN"          # absolute path
  wc -l < "$PLAN"              # line count
  sha256sum "$PLAN"            # SHA256
  git add -N "$PLAN"           # intent-to-add so diff --check can run
  git diff --check -- "$PLAN" && echo "diff --check: CLEAN"
  git diff --stat  -- "$PLAN"
  git reset -q -- "$PLAN"      # undo intent-to-add; index must end as it started
  grep -nE '…|TODO|TBD|FIXME' "$PLAN" || echo "no placeholder tokens"
  git status --short          # confirm ONLY the intended plan file is new/untracked
  ```
  - A repo with `core.autocrlf=true` prints `warning: ... LF will be replaced by CRLF ...` under `git diff --check`. This is a pre-existing setting, NOT a content defect — report it but do not treat it as a blocker. Use `git config core.autocrlf` to confirm.
  - `git add -N` makes an untracked file appear tracked to `diff`, which is why `diff --check` works; ALWAYS `git reset -q --` afterwards or the file stays intent-to-added and pollutes later `git status`/`git add` globs.
  - For an EXISTING tracked file you are rewriting wholesale: `git diff --check` against HEAD works directly (no `-N` needed) once `write_file` changed it; still verify `git status --short` shows only that file.

- **Recovery-disable plans: independent dispatchers need their own fail-closed guards.** When the plan disables AI auto-recovery at the `agent.py` entrypoint, a MINOR_FIXES audit may find OTHER launch routes that source proves do NOT delegate through `agent.py` — e.g. `python_runner/scheduler/recovery_runtime.py` (`main()`/`build_parser()`/`run_target_recovery()`), `python_runner/scheduler/recovery_supervisor.py` (`RecoverySupervisor.run()`/`main()`), `scripts/run-schedule-recovery-watch.ps1` (`Start-Process`), `scripts/register-scheduler-task.ps1` (`Register-ScheduledTask`). An entrypoint guard on `agent.py` alone is INSUFFICIENT. Each must carry its own fail-closed disabled guard (return non-success BEFORE `run_once`/`run_incidents`/`run_target_recovery`/repair-audit-live executors/bridge/subprocess/auto-resume), and no flag/switch may re-enable. Treat as a "design-edits" finding (workflow step 5): touch Files + RED tests + GREEN/implementation + Acceptance + Gate for EACH route. See `references/recovery-disable-route-map.md` and `references/recovery-disable-audit-minor-fixes.md`.
- **Specify ONE shared disabled-state mechanism (don't leave it unspecified).** A MINOR_FIXES audit will flag "how is 'disabled' communicated to R1–R10?" Fix by introducing a single authoritative contract: Python canonical `AUTO_RECOVERY_ENABLED = False` in `automation_core.global_recovery` (no env/CLI/config override) consulted by R1–R6 + `watcher.py`; PowerShell fixed `$AUTO_RECOVERY_ENABLED = $false` (no ENV/CLI override) at the top of each `.ps1` so `Dispatch`/`EnableLiveRecovery`/`Resume`/`EnableAutonomousRecovery`/`EnableRecoveryTask` switches become SUBORDINATE (read only inside an unreachable enabled branch). Mark it as the Task 2/3/9 IMPLEMENTATION CONTRACT — do NOT claim the constant exists in baseline (current `global_recovery.py` has `GlobalRecoveryPolicy` but no switch). Re-enable is OUT OF SCOPE (later separately-authorized release change). Detail in `references/recovery-disable-audit-minor-fixes.md`.
- **R5 RED validity trap: `store_true` flags.** `recovery_runtime.main()` `--resume`/`--dispatch`/`--enable-live-recovery` are ALL `store_true` (default False). Invoking `main()` WITHOUT them already blocks internally → the RED test PASSES on baseline → invalid RED. The valid RED invokes `main()` with ALL THREE enabling flags (`['--dispatch','--enable-live-recovery','--resume']`, plus minimal non-watch mode) so unguarded source constructs/activates the runtime and attempts dispatch → FAILS pre-fix. The guard sits ABOVE `build_parser`/`activate`/`run`, so the flags cannot bypass it. A parser-only test (`test_recovery_runtime_parser_flags_resolvable`) is REGRESSION-ONLY, never a valid RED node.
- **R6 locator: public `RecoverySupervisor.run()` (~L2126) delegates to `_run()` (~L2149); guard BEFORE both + `main()` (~L2355).** Audit may mislabel `_run()` as `run()`. Guarding only the internal `_run()` is insufficient — workers may call `run()`/`main()` directly. RED invokes the public `run()` with `enable_live_recovery=True` (and required executors/artifact_root) and asserts uncalled executors + `main()` guarded.
- **R7/R8 PowerShell tests are STATIC TEXT/ORDERING SCANS, not runtime mocks.** The `.ps1` cannot execute in CI; the Python tests read the `.ps1` CONTENT and assert the disabled branch short-circuits before `Start-Process`/action-build. They do NOT execute PowerShell, do NOT mock a runtime process call, do NOT register a task. Acceptance = SOURCE-LEVEL proven; actual PowerShell/installed-task behavior remains NOT PROVEN (deployment-gap risk). Never write "the Python test mocks the process call / inspects the generated action string at runtime" — that implies behavior the test doesn't exercise.

The real invocations are in `Watcher.process_failure()` (~L478): `self.bridge.apply_recovery` (~L564) / `recapture` (~L572) / `retry` (~L581) / `verify` (~L590).
