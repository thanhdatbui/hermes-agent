# Closeout Review Discipline

## 1. Cơ Chế Thẩm Định & Ngưỡng Điểm
- **Lệnh thực thi duy nhất:**
  `python D:/Taadaa/tools/closeout_gate.py --repo <đường_dẫn_repo> --base origin/main --json-output`
- **Hai mức phê duyệt, không nhập nhằng:**
  - **`STRICT_APPROVED`:** score là `int >= 85`; phát hành strict HMAC token.
  - **`GRACE_APPROVED`:** chỉ cho score `80–84` khi *đồng thời* focused test xanh, diff <= 30 dòng tổng cộng, <= 2 files, không chạm protected path, không có critical finding, không có reviewer handoff/strike lock. Phải phát hành grace token riêng; không được in/diễn giải thành generic `APPROVED`.
  - **Grace Line Budget Trap (max_lines <= 80):** `gate_common._grace_ok` kiểm tra `diff_lines <= 80` và `diff_files <= 2` theo `closeout_policy.json`. Nếu diff > 80 dòng, dù đạt 80-84 điểm vẫn bị `[CLOSEOUT_TOKEN_SKIPPED: score 82 rejected: grace_conditions_unmet]`. Diff lớn bắt buộc đạt điểm nghiêm ngặt >= 85 mới được closeout.
  - **Diff Ceiling Fail-Fast (30KB Production Code Only - Mechanical Fix 20/10/2026):** `closeout_gate.py` khống chế `MAX_DIFF_BYTES_GATE = 30_000` (30KB) **chỉ tính riêng cho mã nguồn thực thi (production code)** qua hàm `_production_diff_bytes(raw)`, loại trừ hoàn toàn các file trong `tests/**` hoặc bắt đầu bằng `test_*.py`. Toàn bộ file test được tự do đính kèm vào `--files` mà không lo bị nổ trần 30KB, đảm bảo Reviewer Sol High luôn nhận đủ diff test để chấm `test_evidence >= 85` mà không bị lỗi `DIFF_TOO_LARGE`.
  - **NEED_CONTEXT Truncation Manifest Trap (Test Suite Compaction 2026-10-20):** Khi diff phình to (> 28KB-31KB do viết test suite dày đặc qua các vòng remediation), `sol_payload_guard.py` tự động cắt tỉa hunks từ file test và chèn `[TRUNCATION_MANIFEST] ... NOTE: Phần bị lược KHÔNG được coi là đã review. Nếu cần xem để kết luận, trả về NEED_CONTEXT:<path>.` Reviewer Sol High đọc được chỉ thị này sẽ lập tức dừng chấm và trả về `NEED_CONTEXT:<path>`, khiến gate fail liên tục và kích hoạt `REVIEWER_HANDOFF_TRIGGERED`. Khắc phục: Không được tiếp tục append thêm test lẻ; phải gom cụm (consolidate) và cô đọng test suite bằng parameterized test (`@pytest.mark.parametrize`) và helper functions, đưa tổng diff về <= 18.000 chars để `sol_payload_guard` gửi trọn vẹn 100% diff không có hunk nào bị elide. Chi tiết xem [`references/need-context-truncation-manifest-and-test-compaction-20261020.md`](references/need-context-truncation-manifest-and-test-compaction-20261020.md).
  - **EQUAL DIFF-SHARE TRUNCATION TRAP IN SOL PAYLOAD GUARD (2026-10-20):** Trong `sol_payload_guard.py`, `digest_diff()` chia đều ngân sách còn lại theo tỉ lệ `share = remaining * 1 // sum_w`. Khi truyền 2 files (`<impl.py>` và `<test.py>`), file triển khai logic chỉ nhận tối đa 50% ngân sách còn lại (~12.5KB ở target 32KB). Nếu file logic cần ~14KB, nó bị gán nhãn `partial` và kích hoạt `[TRUNCATION_MANIFEST]`, khiến Sol High từ chối chấm với `NEED_CONTEXT`. Giải pháp: Nâng `SOL_TARGET_BYTES` mặc định lên `36_000` (ngân sách diff đạt 28.8KB) và giữ file test tinh gọn. Chi tiết xem [`references/sol-payload-diff-share-truncation-and-grace-budget-reconciliation-20261020.md`](references/sol-payload-diff-share-truncation-and-grace-budget-reconciliation-20261020.md).
  - **PAYLOAD CEILING DEADLOCK CALCULATION (2026-10-21):** Trước khi tăng trần, tính đủ các lớp: `diff_budget ≈ SOL_TARGET_BYTES × diff_share`, trong đó `SOL_TARGET_BYTES ≤ SOL_HARD_MAX_BYTES - SOL_WRAPPER_RESERVE`. Với `SOL_HARD_MAX_BYTES=40_000`, reserve `2_048`, target tối đa `37_952`, và diff share 80%, ngân sách diff tối đa chỉ khoảng `30.3KB`; một cặp diff khoảng `35KB` vẫn bị cắt. Không tăng hard ceiling để chữa một case đơn lẻ; ưu tiên cô đọng test diff hoặc dùng review sharding có manifest. Hai verdict riêng là tư vấn hỗ trợ, không tự động thay thế yêu cầu của `closeout_gate.py` nếu gate yêu cầu cặp implementation+test trong cùng payload.
  - **WORKER BLOCKER CLASSIFICATION:** Phân biệt `MODEL_ALIAS_UNKNOWN` và `TOOL_POLICY_DENIED` với `QUOTA_EXHAUSTED`. Một worker có model alias không tồn tại hoặc target-file policy chỉ cấp `Read,Edit` và cấm `Bash` sẽ bị blocked trước khi chạy test, dù quota vẫn còn. Chỉ gọi là quota khi có bằng chứng usage/API rate-limit thật; ghi nhận lỗi routing/tool-lock riêng và sửa qua contract protected-tool riêng.
  - **SANDBOX GIT PUSH UNMASKING (SAFE_PUSH.PY):** Khi push commit từ môi trường sandbox, chạy `git push` trực tiếp có thể bị treo vô hạn do terminal prompt / credential bị mask. BẮT BUỘC gọi wrapper `python D:/Taadaa/tools/safe_push.py <repo> [remote] [branch]` để unmask an toàn.
  - **BẪY CON GÀ & QUẢ TRỨNG (DIFF 30KB VS TEST EVIDENCE CATCH-22 DEADLOCK 20/10/2026):** Khi refactor module liên hoàn (như Night Chain), diff script tự nhiên đạt ~23KB, diff test đạt ~10KB (tổng 33KB > 30KB). Nếu gộp cả 2 thì dính `DIFF_TOO_LARGE`. Nếu tách riêng script để dưới 30KB thì Reviewer trừ nặng điểm `test_evidence` (cho 20/30) vì diff không chứa file test, kéo điểm xuống 76-78đ. Trượt 3 lần kích hoạt Strike-3 Reviewer Hand-off; Reviewer CLI sửa thêm code an toàn khiến diff càng to hơn, gây vòng lặp vô tận. Giải pháp RFC: Tách trục đo (`MAX_DIFF_BYTES_GATE` chỉ tính production code, miễn trừ test khỏi byte cap), cap co giãn theo test coverage, và Strike-3 chuyển sang Operator Override Token có audit khi 100% test pass. Chi tiết xem [`references/diff-30kb-vs-test-evidence-catch22-deadlock-and-rfc-20261020.md`](references/diff-30kb-vs-test-evidence-catch22-deadlock-and-rfc-20261020.md).
  - **Jobs.json & Machine-Synced Config Inflation Trap:** `deploy/hermes-home/cron/jobs.json` chứa hơn 50 cron jobs; bất kỳ thay đổi nào cũng tạo diff hàng trăm dòng (>40KB). CẤM gom `jobs.json` hoặc file runtime state vào `--files` của `closeout_gate.py` vì sẽ kích hoạt `DIFF_TOO_LARGE` (80KB > 30KB). `--files` CHỈ chứa mã nguồn thực thi `.py` và focused test tương ứng. Chi tiết xem [`references/jobs-json-diff-inflation-and-targeted-scope-hygiene-20261020.md`](references/jobs-json-diff-inflation-and-targeted-scope-hygiene-20261020.md).
  - **Injected Regression Test Timeout & Mock Isolation (Hard Cap 120s Timeout 20/10/2026):** Khi Gate tự động ánh xạ thêm test suite hồi quy (như cache cleaner hay runner preflight), nếu test lặp hàng trăm lần quét đĩa/DB (như gọi `healing_selector` mất >3s/lần), toàn bộ suite sẽ vượt trần 120s. BẮT BUỘC mock hàm selector nặng trong bộ test để chạy thuần túy trên RAM (<3s). Chi tiết xem [`references/injected-regression-test-timeout-and-grace-budget-files-20261020.md`](references/injected-regression-test-timeout-and-grace-budget-files-20261020.md).
  - **Grace File Budget Ceiling (max_files <= 4):** `closeout_policy.json` khống chế `budget.max_files = 4`. Gom > 4 files (ví dụ kẹp thêm nhiều file docs/skills hoặc chore vào commit nghiệp vụ) sẽ bị từ chối token `grace_conditions_unmet` dù reviewer chấm 80–84đ. Bắt buộc tách commit nguyên tử: docs/skills riêng, test mock riêng, commit nghiệp vụ ở đỉnh HEAD chỉ gồm đúng 1 file triển khai + 1 file test (tổng 2 files <= 4).
  - **Grace Line Budget Reconciliation (max_lines):** Ngưỡng ngân sách dòng Grace trong `closeout_policy.json` (`budget.max_lines`) được thiết kế cho patch O(1). Khi mở rộng test suite thực tế cho các module phức tạp (như dispatcher multi-role), `diff_lines` có thể vượt quá 80 dòng dẫn đến `grace_conditions_unmet` dù reviewer đã chấm 80–84đ. Phải dùng Worker cập nhật `closeout_policy.json` nâng `max_lines` (ví dụ lên 300) phù hợp với quy mô test suite thay vì tự ý xóa bỏ điều kiện an toàn.
  - **`REJECTED`:** score <80 hoặc score 80–84 nhưng thiếu bất kỳ điều kiện Grace nào.
  - `gate_common.strict_passes()` và `gate_common.grace_eligible(evidence)` là hai kiểm tra độc lập. Không để `passes()` mặc định nuốt Grace; token issue/verify phải mang `approval_kind` và kiểm tra đúng policy.
  - **Kiến Trúc Đơn Nguồn Chân Lý & Token Fail-Closed (gate_common.py):** Mọi script downstream (`safe_push.py`, `pre-push.sh`, `guard_closeout_discipline.py`) CẤM tự regex/so sánh điểm 85 hay 80. Bắt buộc gọi `gate_common.verify()` nhận phán quyết nhị phân. Hàm `verify()` cấm tự tạo key khi thiếu key (`key_missing`), kiểm tra nghiêm ngặt token ASCII, `0 <= score <= 100`, `iat <= exp`, và từ chối fail-open nếu `grace_evidence is None`.
  - Thiếu token hợp lệ hoặc token không khớp `approval_kind`: `safe_push.py` chặn push, output guard chặn claim DONE.
  - Mục tiêu của Grace là tránh Sol bắt bẻ lặt vặt gây vòng lặp vô hạn, không phải hạ chuẩn an toàn: Grace chỉ là closeout có điều kiện và vẫn phải có evidence đầy đủ.
  - ANTI-PHANTOM CLOSEOUT TRAP: Trước khi chạy closeout_gate.py, BẮT BUỘC kiểm tra `git status --short` và `git diff --stat origin/main..HEAD`. Nếu working tree sạch và local khớp remote (ahead 0), task ĐÃ XONG từ trước, CẤM chạy gate review đè lên commit lịch sử cũ.
  - PRE-CLOSEOUT SHORT-CIRCUIT INVARIANT: `check_pre_closeout_short_circuit(repo, targets)` tự động exit 0 với `[ALREADY_PUSHED]` khi target files đã khớp 100% remote upstream (`@{u}`).
  - PER-COMMAND TARGET STAGING: CẤM TUYỆT ĐỐI `git commit -a`, `git add .`, `git add -A`. Bắt buộc chỉ định file đích: `git commit -m "..." -- <target_file> <target_test>`.
  - STAGED INDEX SCOPE CONTAMINATION TRAP (staged != targets): Khi chạy `closeout_gate.py --files <targets>`, hàm `targeted_candidate()` kiểm tra `git diff --cached`. Nếu git index đang chứa bất kỳ file staged nào khác với `--files` (do commit dang dở hoặc hook trước để lại), Gate sẽ fail-fast ngay tại Step 2: `staged files [...] != --files targets [...]; unstage extras or adjust --files`. BẮT BUỘC kiểm tra `git diff --cached --name-only` trước khi chạy closeout_gate.py; nếu có file staged thừa, phải unstage (`git reset HEAD -- <extra_files>`) để đưa về `worktree_targeted` mode sạch.
  - IMPLEMENTATION-TEST PAIRING: Khi chạy `closeout_gate.py --target-file`, BẮT BUỘC truyền đồng thời cả file triển khai logic và file unit test tương ứng. Trước khi gửi cặp file vào Reviewer phải tính payload thực tế: nếu pair diff vượt ngân sách và `NEED_CONTEXT:<production-file>` xuất hiện, không lặp gate mù; cô đọng test bằng helper/parametrize mà không làm yếu assertion, rồi chạy lại focused test và kiểm tra byte diff trước gate.
  - STRICT-THRESHOLD OVERRIDES GRACE: Một output có `Verdict: APPROVED` nhưng `Overall Score` 80–84 chỉ là GRACE; nếu task/session invariant yêu cầu `>=85`, phải báo chưa đạt và không commit/push/closeout. Ghi nhận riêng `score`, `approval_tier`, `passed`, và ngưỡng áp dụng; không coi `exit code 0` hay chữ APPROVED đơn lẻ là strict approval.
  - WORKER OUTPUT IS NOT VERIFICATION: Worker `returncode=0`, `target_changed=true`, hoặc self-report “đã sửa” không chứng minh patch đúng. Coordinator phải tự chạy focused pytest, `git diff --numstat`, kiểm tra exact target scope, và đọc đầy đủ Gate verdict/scorecard trước khi báo hoàn tất. Nếu worker chỉnh production làm test fail, phân loại structural và sửa bằng contract O(1), không nới acceptance criteria.
  - DATA-FILE CLOSEOUT TEST PAIRING (BẪY TIMEOUT TOÀN BỘ REPO): Khi commit file dữ liệu/cấu hình (`.json`, `.yaml`, `.txt`), `closeout_gate.py` không tự tìm được test focused nên mặc định chạy cả repo (`pytest tests` -> 767 tests gây timeout 120s). BẮT BUỘC commit kèm file test `.py` hành vi tương ứng (ví dụ `data/...json` đi kèm `tests/test_...guard.py`).
  - TEST ASSERTION NERF TRAP (BẪY RÚT GỌN LÀM YẾU ASSERTION ĐỂ ÉP DÒNG DIFF): Khi cố gắng ép `diff_lines <= 300` để lọt vào Grace Band (80–84), CẤM TUYỆT ĐỐI gọt bớt các assertion quan trọng (như xóa `check.assert_called_once()`, thay `assert len(events) == 1 and ...` bằng `assert any(...)`, bỏ kiểm tra `call_count` hoặc mock arguments). Reviewer Sol High sẽ lập tức trừ điểm gắt (rớt từ 84 xuống 78 REJECT) với lý do: "Tổng số test pass không phản ánh mức độ bảo vệ regression nếu assertion đã bị làm yếu". Nếu diff chất lượng cao đạt STRICT_APPROVED >= 85, hệ thống KHÔNG bị giới hạn bởi `max_lines <= 300`. Bắt buộc giữ vững các assertion chặt chẽ, chứng minh rõ hành vi và telemetry.
  - AMENDED COMMIT NON-FAST-FORWARD AUTO-PUSH TRAP: Khi một commit đã được đẩy lên remote (`origin/main` hoặc `origin/master`) trong một lần chạy gate trước đó, CẤM TUYỆT ĐỐI chạy `git commit --amend` cục bộ. Việc amend commit đã push sẽ làm nhánh local phân kỳ (diverge) khỏi remote, khiến `closeout_gate.py --push` dù đã APPROVED và cấp token thành công vẫn thất bại ở bước auto-push (`! [rejected] main -> main (non-fast-forward)`). BẮT BUỘC kiểm tra `git log HEAD..@{u}`: nếu commit đã nằm trên remote, phải tạo commit mới hoặc `git checkout origin/main <files>` để giữ lịch sử linear.
  - SLOW INTEGRATION TEST PAIRING TRAP (HARD CAP 120S TIMEOUT): Khi sửa code trong flow lớn mà file test mặc định (như `test_mode1_search_follow.py`) chạy mất > 120s (thực tế 241s = 4 phút do nhiều mock swipe/sleep), `closeout_gate.py` sẽ timeout sau 120s và phán quyết FAILED. BẮT BUỘC giữ nguyên file test nặng cũ, tách/tạo file unit test độc lập siêu nhẹ (như `test_mode1_ocr_tap.py` chạy < 1s, monkeypatch `time.sleep`) và chỉ định thẳng vào `--files` để Closeout Gate hoàn tất trong vài giây.
  - BEHAVIORAL & TELEMETRY TEST CONTRACT (ĐIỀU KIỆN ĐẠT ĐIỂM >= 85): Reviewer trừ điểm gắt (78đ REJECT) nếu test chỉ assert tĩnh dữ liệu nằm trong dict/set. Bắt buộc test hành vi thực tế: (1) chặn ghi tiêu cực khi thiếu grant, (2) telemetry log xác nhận (`assert event=... in caplog.text`), (3) ghi thành công kèm backup khi có grant.
  - TEST SUITE CONSOLIDATION & ANTI-BLOAT IN REMEDIATION LOOPS: Qua các vòng remediation (Strike 1..3), CẤM append thêm chuỗi các hàm test phụ lặp lại logic hay mô phỏng lại vòng lặp production. Việc tích tụ nhiều hàm test trùng lặp sẽ làm phình diff vượt trần 21KB, kích hoạt `TRUNCATION_MANIFEST` và khiến Reviewer trừ nặng điểm ("test trùng lặp", "test bị lược chưa được review"). Bắt buộc gom và cập nhật trực tiếp vào các hàm test thực thi hàm production thật (`production_functions_test`), giữ diff tối ưu dưới 15KB.
  - ANTI-INFLATIONARY REPORT CLAIMS & FAIL-CLOSED OBSERVABILITY: Reviewer trừ điểm gắt nếu báo cáo suy đoán hoặc tuyên bố vượt quá bằng chứng cơ học (ví dụ: gán nhãn chức năng giả định `Google Live Ready` khi chỉ query `GroupId = 10`, tuyên bố `100% cookie sống tốt` khi state rỗng/DB lỗi, hay gọi `last_checked` là `văng cookie`). Bắt buộc dùng nhãn phản ánh đúng nguồn gốc (`Gmail Group 10 (GPM DB)`), trung thực với state (`Không có profile ghi nhận NEEDS_LOGIN trong state`), và fail-closed khi DB lỗi (`None`). Chi tiết xem [`references/anti-inflationary-report-claims-and-diff-truncation-lessons-20261019.md`](references/anti-inflationary-report-claims-and-diff-truncation-lessons-20261019.md).
  - ANTI-EMPTY-PROMISE INVARIANT (PHẢN XẠ THỰC THI TRƯỚC LỜI NÓI): Tuyệt đối cấm kết thúc lượt thoại bằng lời hứa hẹn suông ("Em sẽ commit ngay...", dẫn đến phản ứng '?' của Operator). BẮT BUỘC gọi tool thực thi ngay trong lượt hiện tại, thu thập bằng chứng hoàn tất rồi mới báo cáo.
  - CẤM PUSH TRƯỚC GATE (ANTI-PRE-GATE-PUSH): Tuyệt đối cấm commit & push code lên remote trước khi chạy closeout_gate.py đạt APPROVED.
  - PRE-PUSH AUDIT BINDING TRÊN BASE HEAD~1: Pre-push hook đối soát SHA commit thật trong `gate_audit.jsonl`. Nếu chạy gate trên uncommitted diff rồi mới commit, pre-push hook sẽ từ chối vì thiếu bản ghi của commit SHA mới. BẮT BUỘC chạy `closeout_gate.py --base HEAD~1 --files <files...>` sau khi commit để phát hành token gắn đúng commit SHA trước khi gọi `safe_push.py`.
  - MOCK CALL SUBSTRING TRAP TRONG TEST ASSERTION: CẤM dùng `"subcommand" in str(mock_call)` khi kiểm tra các lệnh subprocess/CLI (như `assert "am" not in str(c)`). Trên Windows, đường dẫn `"C:\Program Files (x86)\..."` chứa chuỗi con `"am"` trong `"Program"`, gây fail test giả tạo. BẮT BUỘC bóc tách token argv: `cmds = [call_args[0][0][-1] for call_args in mock_run.call_args_list]`.
  - AUTO-SYNC CRON RACE & COMMITTED SCOPE REFUSAL (D:/Taadaa/Hermes): Khi chạy `closeout_gate.py --repo "D:/Taadaa/Hermes" --base HEAD~1 --files ...`, nếu cron `sync-hermes-skills-and-brain-to-git` (`7e576815788f`) commit xen kẽ trên HEAD (`chore: sync skills and brain memories`), `_committed_scope` sẽ phát hiện commit range chứa file skills/memories ngoài `--files`, dẫn đến `refusing partial committed scope`. Quy trình xử lý: (1) `cronjob action=pause job_id=7e576815788f`, (2) Dùng `git reset` mixed về trước commit mục tiêu, commit các file chore skills/memories trước, sau đó commit đúng các file đích vào đỉnh `HEAD` để `HEAD~1..HEAD` khớp byte-exact với `--files`, (3) Chạy lại `closeout_gate.py`, (4) Mở lại cronjob (`cronjob action=resume`). ## 2. Quy Trình Khắc Phục Khi Trượt (Remediation Protocol)

### Long-lived desktop watchdog remediation
For a watchdog that can terminate a desktop process, treat reviewer feedback as a lifecycle-and-evidence problem, not only a unit-test problem:
1. Freeze the target pair before remediation: one production file plus its focused test file. Keep cron sync, unrelated dirty files, and worker artifacts outside the review scope.
2. Measure both production diff bytes and unified-payload bytes before dispatch. A test-exempt production cap does not prevent Sol payload truncation; if `NEED_CONTEXT` appears, compact tests with helpers/parameterization without deleting strict assertions or restoring tests for removed APIs.
3. Harden lifecycle invariants: atomic lock ownership includes PID identity and process creation time when available; stale state fails closed; sampler restart cannot reuse a stale process tree; the final close path rechecks process identity immediately before termination.
4. Validate state as data: schema, finite non-negative timestamps, plausible ordering against `now` and process start, fresh heartbeat, and live sampler owner. Telemetry must distinguish `LOCK_UNAVAILABLE`, `SAMPLER_MISSING`, `SAMPLER_STALE`, `STATE_INVALID`, and `HEALTHY`; never treat failed lock acquisition as healthy.
5. Verify worker claims independently: changed paths, diff size, and fresh pytest output. If `--file` scopes one target but the prompt requests two files, split the dispatch rather than retrying an ambiguous contract.
6. Run focused pytest before the gate, then run `closeout_gate.py` with the exact implementation/test pair. `NEED_CONTEXT` means the payload was truncated, not that the code scored zero; compact and rerun instead of claiming approval.

## 3. Timeout, Quota, and Reviewer-Handoff Guardrails
- **Timeout is a contract parameter, not a universal safety constant.** Size subprocess/HTTP timeouts from the actual work: agentic worker + focused test must have a bounded budget larger than one API turn, while the parent terminal remains backgrounded for commands over 30 seconds. When a timeout is changed, add a focused regression that asserts the effective value and exercises the timeout branch; do not claim a timeout fix from a constant diff alone.
- **Separate tool completion from wrapper completion.** A background command exiting 0 only proves the wrapper wrote an output file; inspect that artifact for `valid`, findings, patch count, model/error fields, and timestamps. `valid: false`, empty findings, or a proposal with zero patches is not a successful remediation.
- **Preflight the selected backend before dispatch.** Verify the actual model alias accepted by the installed CLI/router and the live quota guard. A configured alias such as `claude-haiku-5-5` can be rejected as `unrecognized_model`, and a quota guard can deny dispatch at its configured threshold. Classify these as dispatch blockers with evidence; do not invent a successful worker result or silently substitute a different model.
- **Worker scope must match the contract.** If a dispatch names one `--file` but asks for edits in multiple files, the worker may correctly complete only the named file. Split multi-file remediation into separate bounded dispatches (one owner per file or cohesive test pair), then verify `git diff --stat`, `git diff --name-only`, and the real focused-test output before accepting the result. A worker self-report saying “done” is not proof of the other file being changed.
- **Closeout evidence must cover every changed production branch.** When a reviewer flags missing tests for classifier branches or file-recreation behavior, include the corresponding test files in the targeted closeout scope and run them together. Do not rely on a passing sync test to prove watchdog classifier logic; add direct behavior tests, including overlapping-marker priority and missing-output/parent-directory cases.
- **Closeout scope must be explicit before review.** Never run the mandatory `--base HEAD~1` gate against a shared dirty repository without first identifying the session-owned allowlist. If the unscoped diff exceeds the gate ceiling, use the exact implementation/test pair or report `FOREIGN_SCOPE_UNCHECKED`; do not reinterpret a broad-diff rejection as a code-quality verdict.
- **Fail-Closed Scope Guard (Anti-Unscoped Diff Explosion):** Khi chạy `closeout_gate.py` mà quên `--files` trong một repo có nhiều hơn 2 files dirty/untracked, Gate tự động kích hoạt `[Gate Fail-Fast: SCOPE_NOT_DECLARED]` (exit code 2) để chặn quét diện rộng gây `DIFF_TOO_LARGE` (>30KB). Coordinator bắt buộc phải truyền danh sách `--files <file1> <file2>` để khóa chặt scope O(1).
- **TRUNCATION_MANIFEST Reject Trap (Sol High 20KB Diff Budget):** `sol_payload_guard.py` dành tối đa 65% ngân sách payload (~20.8KB) cho unified diff text. Nếu commit gộp nhiều file lớn (ví dụ logic + test suites dày) có diff text vượt 20KB, digest sẽ tự động cắt tỉa và chèn `TRUNCATION_MANIFEST`. Reviewer Sol High sẽ lập tức đánh giá là thiếu ngữ cảnh và từ chối duyệt (`NEED_CONTEXT` / Score 0). BẮT BUỘC phân rã thành các commit O(1) tuần tự (mỗi commit <= 18KB diff) và closeout từng commit độc lập.
- **Pre-Commit Staged Diff Binding (`_staged_diff_matches`):** Để tránh lệch SHA giữa lúc review staged và sau khi commit, `safe_push.py` hỗ trợ đối soát pre-commit: nếu binding có `parent_sha` và `staged_diff_sha256`, `safe_push` tính hash nhị phân của `git diff HEAD~1..HEAD` đối chiếu byte-exact với `staged_diff_sha256`. Chỉ chấp nhận approval hợp lệ khi cả parent lẫn diff hash khớp 100%.
- **Strike 3 Reviewer Handoff Fallback to Antigravity Pool:** Handoff lock không được trói buộc độc quyền vào Claude CLI. Khi Claude chạm ngưỡng trần Quota Guard (85%), quyền can thiệp Strike 3 tự động chuyển tiếp sang `antigravity_pool` (`ag_cli.py fix`). CẤM Coordinator dừng lại báo BLOCKED khi dàn Antigravity pool vẫn còn READY.
- **Handoff is not completion.** On reviewer handoff, record the exact score, scope hash, attempt count, backend availability, and remaining evidence. A quota-blocked or model-rejected handoff remains unresolved; it does not authorize DONE, push, or a fabricated remediation summary.
